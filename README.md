# ПРОСПОРТ (проект SportHub)

Маркетплейс спортивных услуг — объединяет клубы, секции, студии и тренеров города в единой
экосистеме. Полный цикл для пользователя: поиск → выбор → запись → оплата → отзыв.

## Что уже работает

**Главная — витрина по макету ПРОСПОРТ** (фаза 38): тёмный герой с поисковым виджетом
(выпадашка категорий и популярных видов — счёт по опубликованным в запросе), счётчики площадки
из `/api/stats/overview`, «Сегодня в фокусе», «Как это работает», «Возможности», карусели
«Клубы» и «Тренеры» (шесть и четыре по рейтингу, срез запросом с `limit`), финальный призыв.

**Каталог и поиск** (`/catalog`): поиск и фильтры, живая Яндекс.Карта (капли цвета вида спорта
из базы, карточка выбранной точки, легенда, переключатель тёмной темы), выдача карточек клубов
и тренеров одним `CardSlider` с drag/swipe, ближайшие слоты (сегодня → не началось → есть места
→ те же фильтры, что у выдачи). Мульти-город: города добавляются на ходу, адреса подсказывает
Geosuggest. Публичные detail-страницы `/clubs/[slug]` и `/trainers/[slug]` с недельным
расписанием и знаком «проверено» (подтверждает администратор в модерации).

**Запись на занятия.** Общая точка входа `/booking/[scheduleId]`. FSM из восьми статусов
(`pending` → `confirmed` → `completed` / `no_show` / `unmarked` и три вида отмены), check-in
провайдером, ленивые автопереходы: заявка без ответа гаснет за час до начала, неотмеченное
занятие уходит в `unmarked` через 48 часов. Мест не бывает больше, чем есть: счётчик меняется
одной операцией с условием, повторную запись закрывает индекс базы.

**Авторизация.** Личность приходит только из серверной сессии: таблица `sessions`,
идентификатор в cookie `HttpOnly` + `Secure` + `SameSite=Lax`, в базе — его хеш. Вход сверяет
argon2id. Маршруты закрыты по умолчанию — публичное помечается явно. Ролей у людей нет: кем
человек является на площадке, решает то, чем он владеет — карточкой тренера, клубами или ничем.
Назначаемое различие одно — служебная учётная запись администратора. Есть восстановление пароля
и работа администратора от чужого лица с сохранением следа в журнале.

**Кабинет лица услуг** (`/profile/club/3/*`, `/profile/trainer/7/*`): у каждого лица свой
адрес — владелец трёх клубов даёт ссылку на кабинет одного из них, а не на общий. Сводка с KPI,
инбокс заявок, клиенты с приватными заметками (заметки живут при лице: управляющий уходит —
заметки остаются при клубе), статистика, двусторонние связи тренер↔клуб, публикации с полным
CRUD, отзывы, свой ящик уведомлений и свои настройки уведомлений, раздел финансов. Переключатель
лиц показывается только тем, у кого лиц больше одного.

**Личный кабинет** (`/profile/me/*`): он есть у любого вошедшего, включая владельца зала —
на йогу ходят все. Сводка с ближайшей тренировкой, расписание
с фильтрами и таймлайном, статистика (стрики, часы, разбивка по статусам), избранное, отзывы,
личный ящик уведомлений, настройки.

**Админ-панель** (`/service-portal/*`): сводка, журнал активности с фильтрами, аналитика
на Recharts с фильтром по городу, модерация (скрытие с обязательной причиной, возврат
в каталог, **подтверждение публикации** — знак «проверено» гостю, отзыв с причиной; действия
из одного словаря домена), **очередь надзора** — общая лента событий площадки с отбором по теме
и состоянию разбора, сброс пароля любому пользователю с записью
в журнал. Администратор — отдельная единица, а не человек с признаком: записываться,
писать отзывы и заводить лица услуг ему нельзя. Понадобилось тренироваться — заводит
себе обычную учётную запись.

**Уведомления и обратная связь.** Единый стор уведомлений: счётчик у колокольчика, опрос
сервера, оптимистичная отметка прочтения с откатом при ошибке, удаление поштучно и пачкой,
страницы уведомлений с фильтрами по группам. Ящик адресуется ЛИЦУ: у владельца трёх клубов
их три плюс личный, и уборка в одном не гасит остальные. Настройки уведомлений — тоже по ящикам.
Плюс стек тостов.

**Дизайн.** Система ПРОСПОРТ (макет Figma Make, фаза 38): холст `#f4f6f9`, чернила `#111111`,
лайм `#7ed900` (заливка и текст на тёмной плашке; на светлом — тёмно-зелёный `#3a7000`),
тёплая зона orange/red/gold для отмен, валидации, ожидания и звёзд. Шрифты — стек макета:
Barlow Condensed 900 для латиницы, Inter 900 для кириллицы (так превью Make рисует русские
заголовки), Inter — текст, DM Mono — цифры.
Все цвета — токенами `--ui-*` (сырых нет, сторож), контраст текстов AA по всем страницам.
Бренд — `BRAND_NAME` в домене. Скелетоны загрузки на всех подмаршрутах ЛК и разделах админки.
Вёрстка mobile-first, брейкпоинты по содержимому (480/768/960/1024/1280/1440/1920).

## Второму разработчику — как поднять тот же проект

Всё, что нужно, лежит в репозитории (документы, скилы для ИИ, `.env` с бесплатными ключами
Яндекса, снимок базы стенда). Макет Figma Make (`prosport/`) — локальный референс, при
необходимости передаётся отдельно. После `git clone` и `git checkout phase-38`:

```bash
npm ci                                   # зависимости
npm run db:up                            # PostgreSQL 16 в контейнере (порт 5434)
docker exec -i sporthub_postgres psql -U sporthub -d sporthub < backups/sporthub-dev.sql
                                         # та же база, что на стенде автора (демо-данные,
                                         # пароль у всех учёток sporthub123)
npm run app:up                           # бэкенд и фронт в контейнерах → http://localhost:3000
```

Снимок восстанавливается только в ПУСТУЮ базу (сразу после `npm run db:up` на свежем томе);
если база уже была — `npm run db:reset`, затем снова восстановление. Занятия «сегодня» в
демо-наборе досеваются `npm run db:seed` (безопасно повторять). Вход для ИИ — `CLAUDE.md`.

## Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone <repo-url>
cd <repository-folder>

# 2. Установить зависимости (монорепо, один install на все пакеты)
npm install

# 3. Завести файл окружения бэкенда (адрес базы, ключи карт)
cp apps/api/.env.example apps/api/.env

# 4. Поднять базу в контейнере (порт 5434, вторая база под тесты создастся сама)
npm run db:up

# 5. Собрать общие пакеты и бэкенд
npm run build --workspace @sporthub/types
npm run build --workspace @sporthub/domain
npm run build --workspace @sporthub/api

# 6. Накатить схему на пустую базу
npm run db:migrate:deploy --workspace @sporthub/api

# 7. Наполнить базу набором для разработки
npm run db:seed

# 8. Поднять оба процесса — в двух окнах терминала
npm run start --workspace @sporthub/api   # бэкенд, порт 3001
npm run dev --workspace @sporthub/web     # фронт, порт 3000
```

Открыть http://localhost:3000

Шаги 3–7 нужны один раз: файл окружения и том базы переживают перезапуск. Порядок обязателен —
сид пишет в уже накатанную схему, а бэкенд без `DATABASE_URL` не стартует вовсе.

Ключ Яндекс.Карт для браузера задаётся отдельно, в `apps/web/.env.local`
(образец — `apps/web/.env.example`); без него страницы работают, карта на главной — нет.

Фронт проксирует все обращения к `/api/*` на бэкенд, поэтому в браузере адреса прежние.
Без запущенного бэкенда страницы откроются с честной ошибкой, а не пустым каталогом.

`npm run dev` запускает dev-режим через `apps/web/scripts/run-next.mjs` и webpack.
Turbopack доступен отдельно через `npm run dev:turbo`.

## Команды разработки

Команды из корня монорепозитория работают на всех пакетах сразу; для одного пакета
добавляется `--workspace @sporthub/web` (или `api`).

⚠️ **У `apps/api` скрипта `lint` нет**, а корневой `npm run lint` ходит по пакетам
через `--workspaces --if-present` — то есть бэкенд он не проверяет. Типы бэкенда
проверяет только `npm run typecheck`, и прогонять его надо отдельно.

| Команда              | Описание                                                                  |
| -------------------- | ------------------------------------------------------------------------- |
| `npm run dev`        | Локальный dev-сервер фронта через webpack-wrapper (http://localhost:3000) |
| `npm run dev:turbo`  | Альтернативный dev-сервер через Turbopack для точечной диагностики        |
| `npm run build`      | Production-сборка всех пакетов                                            |
| `npm run start`      | Запуск production-сборки фронта                                           |
| `npm run lint`       | Линтер (ESLint) + проверка типов фронта                                    |
| `npm run typecheck`  | Проверка типов всех пакетов (`tsc --noEmit`)                              |
| `npm run format`     | Форматирование (Prettier)                                                 |
| `npm run test`       | Одноразовый прогон тестов всех пакетов                                    |
| `npm run test:watch` | Vitest в watch-режиме                                                     |
| `npm run start --workspace @sporthub/api` | Запуск бэкенда (порт 3001)                           |

Занятия в нём лежат «сегодня/завтра» относительно дня запуска — на стенде гоняют ежедневно, повтор безопасен |

Обычная работа идёт без контейнера приложения: в контейнере нужна только база, а бэкенд и фронт
запускаются напрямую — так правка исходника видна сразу, без пересборки образа.

⚠️ Машина разработки на ARM, сервер на x86. Образы для сервера собираются
`npm run images:build:server` либо прямо на сервере: нативные модули под чужую платформу
не запускаются.

## Production

Прод-инстанс работает на **reg.cloud VPS** (Москва, Ubuntu 24.04 LTS, 2 vCPU / 2 GB RAM / 40 GB NVMe)
под панелью **FastPanel**.

- **URL:** https://athletehub.ru
- **Сервер:** `95.163.236.239`
- **FastPanel:** https://cv7268081.vps.regruhosting.ru:8888 (login `fastuser`)
- **Webroot:** `/var/www/fastuser/data/www/athletehub.ru/`
- **Стек на сервере:** три контейнера (база, бэкенд, фронт; описаны в `docker-compose.yml`) → nginx reverse-proxy (FastPanel) → Let's Encrypt SSL (auto-renew). Наружу смотрит только фронт; бэкенд слушает петлевой адрес `127.0.0.1:3001`
- **DNS:** домен `athletehub.ru` на Reg.ru, A-запись `@ → 95.163.236.239`
- **Бэкап:** daily snapshot всего VPS на уровне reg.cloud
- **Автозапуск** обеспечивает сам Docker: у всех сервисов `restart: unless-stopped`. pm2 на сервере не используется — иначе после перезагрузки два способа запуска поделили бы между собой порты 3000 и 3001

### Деплой обновлений

```bash
# Локально: собрать образы под платформу сервера (машина разработки ARM, сервер x86)
npm run images:build:server

# Перенести образы на сервер и поднять
docker compose --profile app up -d
```

Порядок при изменении схемы базы: **сначала миграция, потом код**. Аддитивная миграция
безопасна для ещё работающего старого кода; обратный порядок даёт окно, в котором новый код
обращается к колонкам, которых ещё нет. Точные команды наката на боевом — `docker/PRODUCTION.md`, §5.

### Управление на сервере

| Команда                                    | Что делает                  |
| ------------------------------------------ | --------------------------- |
| `docker compose --profile app ps`          | Состояние всех контейнеров  |
| `docker compose --profile app logs -f api` | Журнал бэкенда              |
| `docker compose --profile app logs -f web` | Журнал фронта               |
| `docker compose --profile app restart api` | Перезапустить только бэкенд |
| `docker compose exec db psql -U sporthub`  | Консоль базы                |
| `docker stats`                             | Расход памяти по контейнерам |

### Откат

Способ один — восстановить базу из дампа. Порядок — `docker/PRODUCTION.md`, §8.

⚠️ Дамп снимается **до** выкатки:
`docker compose exec -T db pg_dump -U sporthub sporthub | gzip > дамп.sql.gz`.
Записи, сделанные после снятия дампа, при восстановлении теряются.
