# SportHub — Memory

## Главное правило

> ⭐ **Решение заказчика, действует постоянно и на все фазы.** Всё, что делаем, должно быть
> **масштабируемым, расширяемым, улучшаемым и легко модернизируемым — включая архитектуру базы
> данных.** Не «сделать, чтобы работало», а «сделать так, чтобы к этому потом спокойно достраивали».

Это правило старше любой отдельной задачи. При конфликте «быстрее» против «расширяемо» выигрывает
«расширяемо»; если быстрый путь закрывает дорогу развитию — он не выбирается, а расхождение
проговаривается заказчику.

Что это значит на практике — проверяемо, а не декларативно:

- **Масштабируемость.** Фильтрация, сортировка и постраничность — в запросе к БД, не в памяти;
  под каждый `where` + `orderBy` есть индекс. Ничего не считается «на одного человека в момент»:
  счётчики атомарны, проверка и запись — в одной транзакции.
- **Расширяемость.** Добавить статус, тип документа, продукт, роль или поставщика = правка одной
  константы/словаря, а не семи файлов. Новые параметры API и поля DTO — необязательные, чтобы старый
  клиент пережил выкатку.
- **Улучшаемость.** Один словарь — одно объявление; общая логика — в одном сервисе; форматтеры — в
  одном модуле. Дубли устраняются в той же работе, где найдены, а не «потом».
- **Модернизируемость.** Смена хранилища, СУБД или внешней службы не задевает бизнес-логику:
  реализация прячется за интерфейсом с токеном внедрения (образцы — репозитории
  `USERS_REPOSITORY`, `BOOKINGS_REPOSITORY` и отправитель писем `MAILER` / `Mailer`), схема без
  диалектной специфики, бизнес-код не знает ни про SQL-диалект, ни про почтовый транспорт.
  Единственное место, где интерфейс связывается с реализацией, —
  `apps/api/src/storage/storage.module.ts`.
- **База данных — под тем же правилом.** Поля добавляются, а не переопределяются; уникальность
  обеспечивает БД, а не код; связи и каскады описаны в схеме; миграции аддитивные там, где этого
  достаточно (пересборка таблиц — крайняя мера, она не воспроизводится при смене СУБД).
- **Никаких абстракций «на будущее» без второго потребителя.** Расширяемость — это отсутствие
  препятствий развитию, а не слой ради слоя.

Проекция правила на текущий стек SportHub (что именно проверять в нашем коде) — в
`STACK_OVERVIEW.md`, секция «Главное правило — проекция на наш стек».

## Проект

- **Название:** SportHub
- **Назначение:** Маркетплейс спортивных услуг — объединяет клубы, секции, студии и тренеров города в единой экосистеме. Полный цикл: поиск → выбор → запись → оплата → отзыв.
- **Слоган:** Найдите свой спорт. Свой ритм. Свое сообщество.
- **Документация:**
  - `STACK_OVERVIEW.md` — стек, архитектура, соглашения по коду
  - `PROJECT_STATE.md` — снимок проекта: страницы, API, модели, компоненты, сторы, дерево
  - `PHASES_OVERVIEW.md` — локальная карта фаз, статусов и переходов к активной фазе
  - `project-phases/phase-XX.md` — локальный полный план конкретной активной фазы
  - `feature-docs/` — досье по функциональным доменам; точка входа — `feature-docs/_overview.md` (карта доменов и связи).
    ⚠️ **Каталога на диске нет.** Он в `.gitignore`, то есть жил только локально и из истории
    не восстанавливается. Правила про его синхронизацию ниже действуют, как только каталог
    появится; досье домена авторизации пишется заново — фаза 34 переписала домен целиком.

## Стек

- **Язык:** TypeScript 5.x (строгий режим)
- **Фреймворк:** Next.js 16 (App Router) — фронт (`apps/web`); данные отдаёт отдельный бэкенд, обращения к `/api/*` проксируются на него
- **UI:** React 19 + Tailwind CSS 4
- **Стейт:** Zustand
- **Бэкенд:** NestJS 11 (`apps/api`) — отдельное приложение, отвечает за все данные
- **БД:** PostgreSQL 16 + Prisma 7 (схема `apps/api/prisma/schema.prisma`, соединение через
  драйвер-адаптер `@prisma/adapter-pg`). Доступ к данным только через репозитории `apps/api`;
  связывание токенов с реализациями — `apps/api/src/storage/storage.module.ts`
- **Валидация:** Zod 4
- **Auth:** серверные сессии. Таблица `sessions`, идентификатор в cookie `sh-session`
  (`__Host-sh-session` там, где включён `Secure`), `HttpOnly` + `SameSite=Lax`, в базе — его
  sha256. Вход сверяет argon2id. Личность приходит только из сессии. Ролей нет: колонка
  `users.role` удалена (шаг 35.24), кем человек является — выводится из владения лицами услуг.
  Назначаемое различие одно — вид учётной записи `account_kind` (`person` / `admin`), словарь
  в `packages/domain`
- **Тесты:** Vitest 4; на фронте — Testing Library + jsdom
- **Линтер:** ESLint
- **Форматтер:** Prettier
- **Бандлер:** webpack для `npm run dev`; Turbopack opt-in для dev через `npm run dev:turbo`; build через стандартный `next build`
- **Рантайм:** Node.js 24 (`.nvmrc`, `engines.node >= 24`, образы `node:24-bookworm-slim`)

## Режим работы

**КРИТИЧЕСКИ ВАЖНО — следуй этим правилам ВСЕГДА, без исключений.**

### Вход в контекст

При старте **КАЖДОЙ** сессии выполни все шаги по порядку:

1. `CLAUDE.md` загружен автоматически → проверь секцию «Текущее состояние» (активная фаза, шаг, ветка).
2. Открой **параллельно** все рабочие документы:
   - `PHASES_OVERVIEW.md` — карта фаз и статусов
   - `PROJECT_STATE.md` — снимок проекта
   - `STACK_OVERVIEW.md` — архитектура и соглашения
   - `README.md` — пользовательский обзор
   - `feature-docs/_overview.md` — карта функциональных доменов и их связей (каталога на диске
     сейчас нет — этот пункт выполняется, как только он появится)
3. Если есть активная фаза → открой файл фазы `project-phases/phase-XX.md`.
4. Если работа затрагивает конкретный функциональный домен (карты, auth, booking и т.д.) → открой соответствующий файл домена из `feature-docs/` (карта доменов уже загружена в п.2).
5. Сообщи пользователю: текущий статус, что дальше. **Жди указаний.**

**НЕ** пропускай ни один документ. **НЕ** начинай работу, пока все документы не прочитаны.

### Работа по плану

- Работаем **СТРОГО** по активной фазе, шаг за шагом, по порядку.
- Не читай все phase-файлы подряд без необходимости — по умолчанию достаточно карты фаз и активной фазы.
- Перед стартом новой фазы сначала проверь, что под неё уже создан отдельный `project-phases/phase-XX.md`.
- **НЕ** пропускай шаги, **НЕ** меняй порядок, **НЕ** объединяй шаги.
- **НЕ** забегай вперёд. **НЕ** делай шаги из следующих фаз, пока текущая не завершена.
- Перед началом каждого шага объяви: номер шага, название, что конкретно будешь делать. Подтверждения не жди — оно нужно только по правилам секции «Итерации».

### Итерации

- Работаем непрерывно: лимита «1–3 шага за итерацию» нет, обязательного стопа после каждых
  нескольких шагов — тоже нет.
- Отчёт выводится после каждого завершённого **этапа** (или логически цельной группы шагов):
  - Какие шаги выполнены
  - Какие файлы кода созданы/изменены
  - Какие документы обновлены / проверены (по правилам секции «Синхронизация документации и статусов»)
  - Какой следующий шаг
- **Останавливаемся и ждём заказчика только тогда, когда без его ответа дальше нельзя:**
  открытый вопрос из файла фазы, смена продуктового поведения, необратимое действие
  (удаление данных, выкатка), расхождение с «Главным правилом», которое нельзя решить самому.
- Во всех остальных случаях идём дальше сами, не запрашивая «ок» на каждый шаг.

### Цикл реализации шага

Проект работает в режиме: **`контракт → тест → реализация → green → верификация`**.

Для каждого шага — строго по порядку:

1. **Контракт** — сверь шаг с файлом активной фазы `project-phases/phase-XX.md`. Зафиксируй: что должно появиться, что должно работать, как проверять.
2. **Тест** — напиши тест или проверку для новой логики (API-контракты, бизнес-логика, фильтрация, формы, UI-сценарии). Следуй методологии **Red-Green-Refactor** из скила `.claude/skills/tdd/SKILL.md` — он детализирует этот шаг: CLAUDE.md определяет КОГДА тестировать, скил — КАК именно писать тесты. Справочник антипаттернов: `.claude/skills/tdd/testing-anti-patterns.md`.
3. **Реализация** — напиши код. Тесты должны стать зелёными.
4. **Верификация** — прогони полный чеклист:
   - `npm run format`
   - `npm run lint`
   - `npm run test`
   - `npm run build`
   - `runtime / curl / ручная проверка` строго по сценарию шага из файла активной фазы `project-phases/phase-XX.md`.
   - **сверка с «Главным правилом»** — пройди по чек-листу в `STACK_OVERVIEW.md` → «Главное правило — проекция на наш стек». Если шаг ввёл нарушение (фильтрация в памяти вместо запроса, словарь размазан по файлам, бизнес-логика знает про JSON/SQL, дубль оставлен «на потом») — это не завершённый шаг. Либо чиним здесь же, либо явно фиксируем расхождение в отчёте заказчику.
5. **Шаг завершён** только после успешного прохождения всех пунктов верификации.
6. **Указан тест** - при детализации новой фазы или новых шагов в `project-phases/phase-XX.md` не забывать про тесты

### Синхронизация документации и статусов

- Шаг или фаза считаются завершёнными только после синхронизации документации.
- После **КАЖДОГО** завершённого шага проверь: `CLAUDE.md`, `PHASES_OVERVIEW.md`, текущий `project-phases/phase-XX.md`, `PROJECT_STATE.md`, `README.md`, `STACK_OVERVIEW.md`.
- Если шаг изменил UI, API, маршруты, структуру проекта, команды, ограничения, стек, текущий статус или пользовательские сценарии — обнови соответствующие документы **в той же итерации**.
- **Feature docs:** если шаг затронул функциональный домен, для которого существует файл в `feature-docs/` (изменение, расширение, исправление, рефакторинг) — **обязательно** синхронизируй соответствующий файл домена и проверь связанные домены через `feature-docs/_overview.md`. Обнови секции «Текущая реализация», «Ограничения MVP», «План расширения» и «Связанные фазы» по необходимости. Если изменение затронуло связь между доменами — обнови оба файла и карту `_overview.md`.
- Если документ проверен и изменений не требует, **явно** укажи это в отчёте.
- После **ПОСЛЕДНЕГО** шага фазы, в рамках завершения этого шага, перед финальным отчётом и коммитом, **ОБЯЗАТЕЛЬНО**:
  - обнови `CLAUDE.md` (`Текущее состояние`);
  - обнови `PHASES_OVERVIEW.md` (статус фаз, активную фазу для работы и последний завершённый шаг);
  - обнови текущий `project-phases/phase-XX.md` (чек-лист активной фазы, завершённые пункты и следующий шаг, если это отражено в документе);
  - обнови `PROJECT_STATE.md` (снимок проекта: страницы, API, модели, компоненты, сторы, дерево);
  - обнови `README.md` (по правилам секции «README.md»);
  - обнови `STACK_OVERVIEW.md`, если фаза затронула стек, архитектурные решения, пользовательские поверхности или соглашения по коду;
  - обнови затронутые файлы в `feature-docs/`, если фаза изменила соответствующие функциональные домены.
- **ЗАПРЕЩЕНО** объявлять фазу завершённой и переходить к следующей, пока эти документы не синхронизированы.
- Если обнаружено расхождение между `CLAUDE.md`, `PHASES_OVERVIEW.md`, текущим `project-phases/phase-XX.md`, `PROJECT_STATE.md`, `README.md` и `STACK_OVERVIEW.md`, исправь его сразу, не откладывая на потом.
- **Автообновление:** обновляй секцию «Текущее состояние» АВТОМАТИЧЕСКИ после каждых 3 выполненных шагов и после завершения каждой фазы, не дожидаясь команды. Одновременно синхронизируй `PHASES_OVERVIEW.md`, текущий `project-phases/phase-XX.md`, `PROJECT_STATE.md`, `README.md`, при необходимости `STACK_OVERVIEW.md` и затронутые файлы в `feature-docs/`. Также обновляй всё это, когда пользователь говорит «обнови CLAUDE.md» или «сохрани состояние».

### Совместная работа

- **"помоги"** — дописывай за меня с объяснением что и почему.
- **"проверь"** — ревьюишь код, указываешь на ошибки и как исправить.
- **"объясни"** — объясняй подход и логику перед тем как писать код.

### Код

- **Любой код пишется под «Главное правило»** (секция в начале файла). Прежде чем выбрать решение, проверь: не мешает ли оно достраивать? Быстрый путь, закрывающий дорогу развитию, не выбирается.
- **Комментарии в коде — ОБЯЗАТЕЛЬНЫ и ТОЛЬКО на русском.** Каждый файл должен иметь комментарий в начале с описанием назначения файла. Ключевые функции, хелперы и блоки бизнес-логики должны иметь пояснения. Это касается `//`, `/* */`, JSDoc, TODO, STUB — всё на русском.
- Server Components по умолчанию. `"use client"` — только при интерактивности.
- Вся вёрстка — **mobile-first** и адаптивная. Целевые брейкпоинты: `sm` (480px), `md` (768px), `lg` (1024px), `xl` (1280px), `xxl` (1440px), `2k` (1920px).
- Брейкпоинты выбираем по контенту и сетке, а не под конкретные модели устройств.
- Стили через Tailwind CSS классы в JSX. Семантический HTML обязателен.
- Заглушки помечаем всегда `// STUB:` — чтобы потом легко найти и заменить.
- Все операции с данными — через бэкенд. Страницы ходят через `apps/web/src/lib/server-api.ts`, браузер — обычным `fetch('/api/...')`. Фронт не читает файлы с диска, не импортирует клиент базы и не держит собственных маршрутов — это стережёт `apps/web/src/test/architecture.test.ts`.
- API ответы: `{ success: true, data: ... }` или `{ success: false, error: "..." }`.
- **При создании или изменении любых UI-компонентов и страниц** — следуй стандарту из `.claude/skills/frontend-design/SKILL.md` (дизайн-философия, палитра, адаптивность, семантический HTML).
- **При работе с handoff-bundle от Claude Design** — следуй разделу «Workflow с Claude Design» в `.claude/skills/frontend-design/SKILL.md`. Триггеры: пользователь вставил команду `Fetch this design file ... https://api.anthropic.com/v1/design/...` (кнопка «Send to local coding agent» из Claude Design), либо просит «реализовать дизайн из Claude Design», «портировать макет», «перенести вёрстку из Claude Design». Кратко: `WebFetch` → распаковка в `claude-design/` → читаем `chats/*.md` (intent) и `*Source*.html` (разметка) → переводим в наш стек (Tailwind + React + наши токены), не копируя DOM 1-в-1 → не трогаем компоненты вне scope текущей задачи.
- **При прогоне E2E-чек-листов через Playwright MCP** — следуй правилам из `.claude/skills/e2e-playwright/SKILL.md`. Триггеры: "прогони чек-лист", "запусти E2E", "запусти MCP", "проверь фазу через браузер", "сделай автотест".
- Импорты через алиас `@/`.

## Git

### Коммиты

- После **КАЖДОГО** завершённого шага: `git add` + `git commit` с осмысленным сообщением, но не раздувая текст для него.
- Формат: `тип(модуль): Step X.Y — краткое описание`
- Описание коммита после `тип(модуль):` пиши **ТОЛЬКО на русском языке**. Без исключений. Английский допустим только в префиксе `тип(модуль):`.
- Типы: `feat` (новая функциональность), `fix` (баг), `refactor` (рефакторинг), `chore` (инфраструктура, конфиги), `docs` (документация), `style` (стили/UI)
- Примеры:
  - `chore(infra): Step 1.1 — инициализировать проект через create-next-app`
  - `feat(types): Step 2.1 — описать TypeScript-интерфейсы всех сущностей`
  - `feat(api): Step 3.2 — добавить API клубов с фильтрами и детальной карточкой`
  - `feat(ui): Step 4.2 — создать базовые UI-компоненты`
  - `feat(page): Step 5.9 — собрать главную страницу из всех секций`

### Ветки

- Перед началом **КАЖДОЙ** новой фазы: создай ветку `phase-X` от текущего состояния.
