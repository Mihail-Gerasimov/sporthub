## Проект

- **Название:** SportHub
- **Назначение:** Маркетплейс спортивных услуг — объединяет клубы, секции, студии и тренеров города в единой экосистеме. Полный цикл: поиск → выбор → запись → оплата → отзыв.
- **Слоган:** Найдите свой спорт. Свой ритм. Свое сообщество.
- **Документация:**
  - `STACK_OVERVIEW.md` — стек, архитектура, соглашения по коду
  - `IMPLEMENTATION_PLAN.md` — пошаговый план реализации MVP: 10 фаз

## Стек

- **Язык:** TypeScript 5.x (строгий режим)
- **Фреймворк:** Next.js 16 (App Router) — монолит: фронт + API в `app/api/`
- **UI:** React 19 + Tailwind CSS 4
- **Стейт:** Zustand
- **БД (MVP):** JSON-файлы (`src/data/`), доступ через абстракцию `src/lib/db.ts`
- **Валидация:** Zod
- **Auth (MVP):** Auth-модалка `Вход / Регистрация` на Zustand + localStorage, с типами аккаунта `provider / athlete`. Позже Auth.js / NextAuth.js
- **Линтер:** ESLint
- **Форматтер:** Prettier
- **Бандлер:** Turbopack (дефолтный в Next.js 16)
- **Рантайм:** Node.js 20 LTS

## Режим работы

**КРИТИЧЕСКИ ВАЖНО — следуй этим правилам ВСЕГДА, без исключений.**

### Работа по плану

- Работаем **СТРОГО** по `IMPLEMENTATION_PLAN.md`, шаг за шагом, по порядку.
- **НЕ** пропускай шаги, **НЕ** меняй порядок, **НЕ** объединяй шаги.
- **НЕ** забегай вперёд. **НЕ** делай шаги из следующих фаз, пока текущая не завершена.
- Перед началом каждого шага: скажи номер шага, название, и что конкретно будешь делать. **Жди подтверждения.**

### Итерации

- За одну итерацию делаем **МАКСИМУМ 1–3 шага**.
- После каждых 1–3 шагов — **ОБЯЗАТЕЛЬНЫЙ СТОП**. Выведи отчёт:
  - Какие шаги выполнены
  - Какие файлы кода созданы/изменены
  - Какие документы обновлены (`CODEX.md`, `IMPLEMENTATION_PLAN.md`, `README.md`, `STACK_OVERVIEW.md`)
  - Какие документы проверены и не потребовали изменений
  - Какой следующий шаг
- После отчёта — **ЖДИ** команды "ок", "продолжай", "давай дальше" или другого указания. Без команды — не продолжай.

### Проверка и верификация

- На текущем этапе проект работает в режиме: **`contract-first -> implementation -> mandatory verification`**.
- Перед началом реализации каждого шага сначала сверь его с `IMPLEMENTATION_PLAN.md`.
- До написания кода зафиксируй контракт шага:
  - что должно появиться;
  - что должно работать;
  - как именно это будет проверяться по сценарию из `IMPLEMENTATION_PLAN.md`.
- Только после этого пиши код.
- После реализации обязательна полная верификация:
  - `format`;
  - `lint`;
  - `build`;
  - `runtime / curl / ручная проверка` строго по сценарию шага из `IMPLEMENTATION_PLAN.md`.
- Шаг считается завершённым только после успешной проверки.

### Синхронизация документации и статусов

- Шаг или фаза считаются завершёнными только после синхронизации документации.
- После **КАЖДОГО** завершённого шага проверь: `CODEX.md`, `IMPLEMENTATION_PLAN.md`, `README.md`, `STACK_OVERVIEW.md`.
- Если шаг изменил UI, API, маршруты, структуру проекта, команды, ограничения, стек, текущий статус или пользовательские сценарии — обнови соответствующие документы **в той же итерации**.
- Если документ проверен и изменений не требует, **явно** укажи это в отчёте.
- После **ПОСЛЕДНЕГО** шага фазы, в рамках завершения этого шага, перед финальным отчётом и коммитом, **ОБЯЗАТЕЛЬНО**:
  - обнови `CODEX.md` (`Текущее состояние`);
  - обнови `IMPLEMENTATION_PLAN.md` (чек-лист текущей фазы, завершённые пункты и следующий шаг / следующую фазу, если это отражено в документе);
  - обнови `README.md` (прогресс реализации, "Что уже работает", структура проекта, команды, если изменились);
  - обнови `STACK_OVERVIEW.md`, если фаза затронула стек, архитектурные решения, пользовательские поверхности или соглашения по коду.
- **ЗАПРЕЩЕНО** объявлять фазу завершённой и переходить к следующей, пока эти документы не синхронизированы.
- Если обнаружено расхождение между `CODEX.md`, `IMPLEMENTATION_PLAN.md`, `README.md` и `STACK_OVERVIEW.md`, исправь его сразу, не откладывая на потом.

### Совместная работа

- **"помоги"** — дописывай за меня с объяснением что и почему.
- **"проверь"** — ревьюишь код, указываешь на ошибки и как исправить.
- **"объясни"** — объясняй подход и логику перед тем как писать код.

### Переход к TDD

- Пока тестовая среда не подключена, strict TDD не обязателен для каждого шага.
- После выполнения шага **Step 3.4 — Подключить тестовую среду** режим работы меняется на: **`test first -> code -> green`**.
- С этого момента для новой логики сначала создаётся тест или проверка, затем пишется реализация.
- Это правило относится к API-контрактам, бизнес-логике, фильтрации, формам и пользовательским UI-сценариям.
- После подключения тестовой среды наличие зелёных тестов не отменяет обязательные `format`, `lint`, `build` и runtime-проверки.
- До появления тестовой среды запрещено пропускать этап формализации контракта и обязательной верификации.

### Код

- Комментарии в коде — на русском.
- Server Components по умолчанию. `"use client"` — только при интерактивности.
- Вся вёрстка — **mobile-first** и адаптивная. Минимальные целевые диапазоны: `base` (<640px), `sm` (640px+), `md` (768px+), `lg` (1024px+), `xl` (1280px+), `2xl` (1536px+).
- Брейкпоинты выбираем по контенту и сетке, а не под конкретные модели устройств.
- Заглушки помечаем `// STUB:` — чтобы потом легко найти и заменить.
- Все операции с данными — через `lib/db.ts`. Напрямую JSON не читаем.
- API ответы: `{ success: true, data: ... }` или `{ success: false, error: "..." }`.
- Импорты через алиас `@/`.

## Git

### Коммиты

- После **КАЖДОГО** завершённого шага: `git add` + `git commit` с осмысленным сообщением.
- Формат: `тип(модуль): Step X.Y — краткое описание`
- Описание коммита после `тип(модуль):` пиши **на русском языке**.
- Типы: `feat` (новая функциональность), `fix` (баг), `refactor` (рефакторинг), `chore` (инфраструктура, конфиги), `docs` (документация), `style` (стили/UI)
- Примеры:
  - `chore(infra): Step 1.1 — инициализировать проект через create-next-app`
  - `feat(types): Step 2.1 — описать TypeScript-интерфейсы всех сущностей`
  - `feat(api): Step 3.2 — добавить API клубов с фильтрами и детальной карточкой`
  - `feat(ui): Step 4.2 — создать базовые UI-компоненты`
  - `feat(page): Step 5.9 — собрать главную страницу из всех секций`

### Ветки

- Перед началом **КАЖДОЙ** новой фазы: создай ветку `phase-X` от текущего состояния.
- Работай в ветке фазы. После завершения — пользователь сам решит когда мержить.

### Запреты

- **НЕ** делай `git push` — пользователь сам решит когда пушить.
- **НЕ** делай `git merge` — пользователь сам решит когда мержить.
- **НЕ** делай force push, rebase или другие деструктивные операции.
