# SportHub — Стек и Технологические Решения

> Этот документ фиксирует полный технологический стек проекта.
> Любые изменения стека должны быть обоснованы и отражены здесь.

---

## Архитектура

**Монолит на Next.js** — фронтенд и API в одном проекте (`app/api/`).
Один сервер, один деплой, без CORS-проблем. Для MVP — оптимально.

**Путь масштабирования:**

```
JSON (fs/lowdb)     → PostgreSQL + Prisma ORM
Монолит (Next.js)   → Вынос бэкенда в NestJS
Без кэша            → Redis (кэш, очереди)
```

### Текущая предметная модель каталогов

С Phase 8 проект переводится с клубо-центричной схемы на две независимые каталоговые модели:

- клубы и услуги клуба;
- тренеры и услуги тренера.

Для этого в доменной модели вводится отдельная сущность услуги (`Offering`), а маршрут `/booking/[scheduleId]` сохраняется как единая точка входа в запись на конкретный слот. В рамках Phase 8 типы, fake data, `db.ts`, API-контракты и сама booking page были переведены на общий slot-based сценарий для club и trainer услуг. В рамках Phase 9 главная страница уже перестроена под dual discovery `clubs | trainers`, включая отдельную trainer-выдачу, trainer-карту, популярный блок и доступные окна тренеров. Следующий этап — следующая кабинетная / продуктовая поверхность Phase 10.

## Текущие пользовательские поверхности MVP

- `/` — главная страница с dual discovery `clubs | trainers`, фильтрами, fake-картой, подборками и блоком доступных слотов
- `/clubs/[id]` — публичная страница клуба с деталями, расписанием, тренерами и отзывами
- `/booking/[scheduleId]` — общая slot-based страница записи для club и trainer услуг
- `/profile/athlete` — личный кабинет спортсмена, доступный только авторизованному `athlete`
- `Header -> Войти` — auth-модалка с табами `Вход / Регистрация`

### UI и стилизация

| Технология       | Версия | Назначение                                                                                                                                                                             |
| ---------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tailwind CSS** | 4.2.1  | Utility-first CSS-фреймворк. Стили пишутся классами прямо в JSX: `className="flex items-center gap-4 p-6"` вместо создания CSS-файлов. `create-next-app` с Tailwind ставит 4-ю версию. |

> **Важно — Tailwind 4 vs 3: ключевые отличия.**
> Tailwind 4 — это серьёзное обновление, и он работает иначе, чем 3-я версия:
>
> - **Нет `tailwind.config.ts`** — конфигурация переехала в CSS. Кастомизация темы (цвета, шрифты, брейкпоинты) делается через директиву `@theme` прямо в `globals.css`, а не в JS-файле конфига. Если после `create-next-app` нет `tailwind.config.ts` — это нормально, так и задумано.
> - **Нет массива `content`** — Tailwind 4 автоматически сканирует файлы проекта, сам находит классы. Не нужно вручную указывать пути к файлам.
> - **CSS-first подход** — вместо `@tailwind base; @tailwind components; @tailwind utilities;` в globals.css пишем `@import "tailwindcss";` — одна строка.
> - **Быстрее** — движок переписан на Rust, билды до 5x быстрее, инкрементальные — до 100x.
> - **Новые возможности из коробки** — container queries, 3D-трансформы, conic/radial градиенты, `@starting-style` для анимаций.
>
> Если в гайдах/туториалах видишь `tailwind.config.js` с массивом `content` — это Tailwind 3, не путай.

### Адаптивность и брейкпоинты

Проект верстается по принципу **mobile-first**: базовые стили пишутся без media queries, затем усиливаются для больших экранов. За основу берём актуальные дефолтные брейкпоинты Tailwind 4 и используем их как проектный стандарт.

| Alias  | Min width | Media query                   |
| ------ | --------- | ----------------------------- |
| `base` | `0px`     | базовые стили без media query |
| `sm`   | `640px`   | `@media (min-width: 640px)`   |
| `md`   | `768px`   | `@media (min-width: 768px)`   |
| `lg`   | `1024px`  | `@media (min-width: 1024px)`  |
| `xl`   | `1280px`  | `@media (min-width: 1280px)`  |
| `2xl`  | `1536px`  | `@media (min-width: 1536px)`  |

Практическое правило:

- сначала проектируем `base` для телефонов;
- на `sm` и `md` перестраиваем сетки и интервалы для больших телефонов и планшетов;
- на `lg` и выше раскладываем desktop-структуру;
- если конкретному экрану не нужен переход на одном из диапазонов, лишний брейкпоинт не добавляем.

Базовый набор media queries для CSS:

```css
@media (min-width: 640px) {
  /* sm */
}

@media (min-width: 768px) {
  /* md */
}

@media (min-width: 1024px) {
  /* lg */
}

@media (min-width: 1280px) {
  /* xl */
}

@media (min-width: 1536px) {
  /* 2xl */
}
```

### Стейт-менеджмент

| Технология  | Назначение                                                                                                                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Zustand** | Минималистичный стейт-менеджер для React. Проще Redux в разы — нет boilerplate. Создаётся store за 10 строк. Хранит **только клиентское состояние**: текущие фильтры поиска, состояние UI (модалки, сайдбар), данные формы записи. Серверные данные (клубы, тренеры) **не храним** в Zustand — их получаем через fetch в Server Components. |

### Данные (БД)

| Технология          | Назначение                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **JSON-файлы (fs)** | База данных на этапе MVP — локальные `.json` файлы в `src/data/`. Нулевая настройка: не нужно ставить PostgreSQL, создавать миграции, настраивать подключение. Вся работа с данными идёт через абстракцию `src/lib/db.ts` — ни один компонент не читает JSON напрямую. Структура данных проектируется как будущие таблицы PostgreSQL (id, внешние ключи, нормализация). Когда придёт время — меняем только `db.ts`, остальной код остаётся. |
| **Zod**             | TypeScript-first библиотека валидации. Валидирует всё, что приходит в API routes — тело запроса, query-параметры. Из Zod-схем выводятся TypeScript-типы (`z.infer<typeof schema>`) — один источник правды для валидации и типов. Работает и на сервере, и на клиенте (формы).                                                                                                                                                               |

### Аутентификация

| Технология                     | Назначение                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Zustand + localStorage**     | Текущая MVP-авторизация проекта. Используется одна auth-модалка с табами `Вход` / `Регистрация`, обязательным выбором типа аккаунта (`provider` / `athlete`), клиентской валидацией форм и persistence в `localStorage`. После успешного submit в store сохраняются `user`, `accountType`, `isAuthenticated`. Header и кабинет спортсмена читают это состояние напрямую. Подключаем, когда понадобится реальная серверная авторизация: Credentials Provider (email + пароль) или OAuth, сессии, middleware, защита маршрутов и полноценная проверка пользователя.                                                                                                                                              |

## Соглашения по коду

- **Язык кода:** TypeScript (строгий режим), комментарии на русском
- **Компоненты:** Server Components по умолчанию. `"use client"` — только где нужна интерактивность (формы, фильтры, модалки, обработчики событий)
- **Стили:** только Tailwind-классы, кастомный CSS запрещён (кроме `globals.css` для Tailwind-директив и `@theme`)
- **Адаптивность:** все пользовательские экраны и компоненты должны быть адаптивными, mobile-first, с опорой на брейкпоинты `sm` `md` `lg` `xl` `2xl`
- **Импорты:** через алиас `@/` — `import { Club } from '@/types'` вместо `../../../types`
- **Именование:** компоненты `PascalCase.tsx` (`ClubCard.tsx`), утилиты/хелперы `camelCase.ts` (`formatPrice.ts`)
- **Работа с данными:** все операции с JSON через `lib/db.ts`. Напрямую `fs.readFile` в компонентах и API routes — запрещено
- **Заглушки:** помечаем комментарием `// STUB:` — чтобы потом легко найти поиском и заменить на реальную реализацию
- **API ответы:** единый формат `{ success: true, data: ... }` или `{ success: false, error: "..." }`
- **Принцип разработки:** Данные → API → UI. Сначала JSON-структура, потом эндпоинт, потом компонент
