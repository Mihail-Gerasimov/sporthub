## Главное правило — проекция на наш стек

⭐ Формулировка правила — в `CLAUDE.md`, секция «Главное правило» (решение заказчика, действует постоянно и на все фазы, старше любого документа и любой задачи). Здесь — как оно проверяется именно в нашем коде.

| Принцип | Что проверяем в SportHub |
| ------- | ------------------------ |
| **Масштабируемость** | Отбор, порядок и постраничность выполняет **запрос**, а не код после чтения. Проверяется не на глаз: у горячей таблицы `idx_scan` обязан расти, а не стоять на нуле (`pg_stat_user_tables`). Под каждый `where` + `orderBy` есть индекс, и у каждого индекса есть запрос — мёртвый индекс дорожит каждую вставку и не ускоряет ничего. Счётчик мест меняется одной операцией с условием (`changeBookedCount` в `apps/api/src/repositories/prisma/entities.repository.ts`), никогда «прочитал → посчитал → записал». |
| **Расширяемость** | Новый статус записи, вид учётной записи, полномочие, тип уведомления, вид спорта или политика отмены = правка **одной** константы. Новый ВИД ЛИЦА услуг (площадка, мероприятие) — значение в `CatalogOwnerType` плюс строка в словаре разделов кабинета, а не правка каждого потребителя. Эталоны в `packages/domain/src`: `booking-status.ts`, `booking-fsm.ts`, `notification-types.ts`, `discipline-config.ts`, `account-kind.ts`, `permissions.ts`, `session-policy.ts`, `link-status.ts`; справочники (города, виды спорта, теги, удобства, специализации, форматы работы) — таблицы базы. Новые параметры API и поля фильтров — только необязательные, чтобы прежние вызовы означали ровно то же (образцы: `BookingsFilter`, `ScheduleFilter`, `PublicationStatusFilter`). Контракт `{ success, data }` / `{ success, error }` не ломаем. |
| **Улучшаемость** | Один словарь — одно объявление. Проверка простая: если один и тот же смысл подписан в двух файлах, копии **уже разошлись** или разойдутся. Общая логика — в `packages/domain`, форматтеры — в одном модуле. Найденный дубль устраняется в той же работе, где найден. Полноту словарей держит тип: `Record<AccountKind, …>` не соберётся, пока новому виду учётной записи не назначили срок сессии и подпись. |
| **Модернизируемость** | Бизнес-логика не знает ни про файлы, ни про SQL-диалект. Клиент базы за границей: его импортируют только `apps/api/src/repositories/prisma/**`, и это стережёт `database-boundary.test.ts`. Связывание токенов с реализациями — одно место, `apps/api/src/storage/storage.module.ts`: там же выбирается и отправитель писем (`MAILER`). Что сервисы не знают о хранилище, стережёт `storage-boundary.test.ts`. |
| **База данных** | Поля добавляются, а не переопределяются. Уникальность и целостность обеспечивает БД: почта, повторная запись, действующая связь тренер↔клуб, адрес-ссылка, город, оценка на посещение, «занятых мест не больше вместимости». Связи и каскады описаны в схеме. Перечисления — строковыми колонками, без типов БД: иначе словарь оказался бы в двух местах. Миграции аддитивные; пересборка таблицы — крайняя мера. |
| **Без абстракций впрок** | Слой вводится, когда у него есть второй потребитель или уже назначенная замена реализации. Метод, который зовут только тесты, — не абстракция, а мёртвый код. |

### Действующие ограничения

Что правилу пока не отвечает. Список закрытый: каждый новый шаг обязан его **не увеличивать**.

- **Версионирования адресов нет.** `/api/v1/` не заведён; единственная гарантия совместимости — необязательность новых параметров и неизменность формы ответа.
- **Счётчики частоты обращений — в памяти процесса.** Это стандартное хранилище `@nestjs/throttler`, и при одном процессе бэкенда счётчику негде разъезжаться. Второй процесс даст два независимых счётчика, то есть удвоенный предел; переезд на общее хранилище — это провайдер `ThrottlerStorage` в `AppModule`, без правки маршрутов.

  Когда возьмём: вынести на свой маршрут, фильтры — в строку адреса (чтобы ссылкой на отфильтрованную выдачу можно было поделиться — сегодня нельзя), постраничность в запросе (в фазе 38 как раз появляются `limit`/`offset`/`orderBy`, пункт 6 «Входит»), сохранить главную как витрину.

## Архитектура

- **Два приложения в монорепозитории**: `apps/web` (Next.js, страницы) и `apps/api` (NestJS, данные). Общий код — в пакетах `packages/types` (типы и константы), `packages/domain` (доменные правила без ввода-вывода) и `packages/fixtures` (тестовые данные).
- **Данные лежат в PostgreSQL, и знает о них только бэкенд.** Файлового хранилища в проекте нет: ни каталога данных, ни переключателя реализации.
- **Как связаны приложения**: фронт проксирует `/api/*` на бэкенд (`apps/web/next.config.ts` → `rewrites`), поэтому адреса в браузере не зависят от того, где живёт бэкенд. Страницы при отрисовке на сервере ходят туда же через `apps/web/src/lib/server-api.ts` — он же пробрасывает cookie сессии.
- **Слои бэкенда**: контроллер (разбор запроса и форма ответа) → сервис (правила) → репозиторий (одна коллекция) → база. Репозиторий не знает про HTTP, контроллер не знает про SQL.
- **Атомарность**: многошаговые операции (запись на занятие, публикация, каскадное удаление, выдача отзыва) идут через `runInTransaction` (`apps/api/src/storage/prisma-transaction.ts`). Транзакционный клиент Prisma кладётся в контекст выполнения (`AsyncLocalStorage`), поэтому репозитории не тащат его через свои сигнатуры. Вложенный вызов **присоединяется** к уже открытой транзакции: Prisma вложенных транзакций не поддерживает, и наивный перенос дал бы взаимную блокировку на пуле.
- **Модель каталога**: две независимые каталоговые линии — клубы и услуги клуба, тренеры и услуги тренера; между ними двусторонние связи тренер↔клуб.
- **Точка записи**: `/booking/[scheduleId]` — общая entry point для slot-based записи.
- **Как наполняется каталог**: `clubs / trainers / offerings / schedule / reviews` — через публикацию из кабинета лица (`/profile/<вид>/<номер>/publications`); `bookings` — через API записей (`POST/DELETE /api/bookings` → сервис записей → репозитории → PostgreSQL).
- **Публичный detail-routing**: `/clubs/[slug]` и `/trainers/[slug]`.
- **Личность приходит только из серверной сессии.** Ни один маршрут не принимает идентификатор пользователя из тела или строки запроса — это стережёт `identity-boundary.test.ts`.
- **Страницы без статической оптимизации** (`dynamic = 'force-dynamic'`): `/`, `/clubs/[slug]`, `/trainers/[slug]`, `/booking/[scheduleId]`, `/reset-password`, лейауты и все подмаршруты кабинетов, лейаут и разделы админ-панели. Корневые
  `/profile/me` и `/profile/<вид>/<номер>` — `redirect()`-страницы на свой `/dashboard`.
- **Кабинеты адресные** (шаг 35.31). `/profile/me/*` — человек: номера в адресе нет
  и не будет, человек в сессии ровно один и «чужого себя» в адресе не выразить.
  `/profile/<вид>/<номер>/*` — лицо услуг, и номер здесь обязателен: у владельца трёх
  клубов три разных кабинета. Владение сверяет `requireOwner` в лейауте, ДО любого
  похода за данными, и он **отдаёт само лицо** — второй проверки, которая маскировала
  бы снятие первой, в лейауте нет. Прежние адреса живут: `/profile/athlete/*` уводит
  постоянным ответом (соответствие одно для всех и навсегда), `/profile/provider/*` —
  временным (назначение зависит от того, кто открыл ссылку).

Функциональные домены (auth, admin, booking, карты, публикация, данные) → `feature-docs/_overview.md`.

### Хранилище данных

- **PostgreSQL 16 в контейнере.** Порт 5434 на локальном адресе: 5432 занимают штатные установки, 5433 — соседний проект на той же машине.
- **Prisma 7** — схема в `apps/api/prisma/schema.prisma`, миграции рядом, строка подключения для миграций — в `apps/api/prisma.config.ts`. Клиент собирается в CommonJS (`moduleFormat = "cjs"`): по умолчанию генератор выдаёт код для ESM с `import.meta.url`, и собранный бэкенд падал бы при запуске, а не при сборке.
- **Соединение через драйвер-адаптер** (`@prisma/adapter-pg` + `pg`). Размер пула — явная переменная `DATABASE_POOL_SIZE`, а не хвост строки подключения.
- **Единственное место, где написано, где лежат данные** — `apps/api/src/storage/storage.module.ts`. Там токены репозиториев связываются с реализациями на Prisma и там же выбирается отправитель писем. Реализация хранилища одна; возврат выбора хранилища краснит `storage-boundary.test.ts`.
- **29 таблиц.** Перечисления — строковые колонки, а не типы базы: словарь остаётся один, в `packages/domain`, и добавление статуса не требует миграции.
- **Уникальность обеспечивает база**, а не проверка в коде: занятая почта, повторная запись на занятие, вторая действующая связь тренера с клубом, одна оценка на посещение. Тексты ошибок наружу прежние — перевод стоит в реализации репозитория, потому что один код нарушения обязан давать разные сообщения, и различить их можно только по контексту операции.
- **Счётчик занятых мест меняется одной операцией с условием.** Проверка «мест хватает» стоит в самом запросе; проверка перед записью её не заменяет — между ней и записью всегда есть щель.
- **Локаль сравнения строк — ICU `ru-RU`.** Задаётся один раз при создании тома и потом меняется только пересозданием кластера. Порядок кириллицы совпадает с `localeCompare` символ в символ.
- **Тестовая база отдельная** (`sporthub_test`, создаётся при первом подъёме тома скриптом `docker/postgres-init/01-test-database.sql`), у каждого исполнителя тестов своя схема. Обвязка тестов принудительно подменяет адрес базы — попасть в рабочую тест не может.

### Авторизация и безопасность

- **Серверные сессии.** Таблица `sessions`; идентификатор сессии уходит в cookie `HttpOnly` + `Secure` + `SameSite=Lax` + `Path=/`, в базе хранится его sha256 (`apps/api/src/common/secret-token.ts`). Все настройки cookie — в одном месте, `apps/api/src/auth/session-cookie.ts`. При TLS имя получает префикс `__Host-`: браузер тогда запрещает поддомену её ставить и подменять.
- **Сроки жизни** — один словарь `SESSION_POLICY` в `packages/domain/src/session-policy.ts`: предельный срок от входа и срок бездействия, отдельно по виду учётной записи (у администратора сутки бездействия против двух недель у человека).
- **Пароли — argon2id** (`@node-rs/argon2`). Вход отвечает одним сообщением на все отказы и выполняет сверку даже для несуществующей почты, иначе её видно по времени ответа. Проверки идут через ограничитель параллелизма: каждая берёт 19 МБ, и без очереди сотня одновременных входов съедает память.
- **Закрыто по умолчанию.** Глобальный `SessionGuard` через `APP_GUARD`: маршрут без пометки `@Public` требует сессии. Это стережёт `route-guard.test.ts`.
- **Ролей нет** (шаг 35.24): колонка `users.role` удалена, «тренер» и «владелец клуба» выводятся из владения лицами услуг. Осталось одно назначаемое различие — вид учётной записи `users.account_kind` (`person` / `admin`, словарь `packages/domain/src/account-kind.ts`, `CHECK` в базе). Шесть админских возможностей — `packages/domain/src/permissions.ts` плюс декоратор `@Requires`; всё остальное решает владение в `AccessService`. Возврат роли краснит `apps/api/src/test/role-boundary.test.ts`.
- **Работа от чужого лица** выполняется на сервере: сессия хранит две личности, права считаются по цели, журнал пишется на настоящего администратора.
- **Ограничение частоты** (`@nestjs/throttler`, обвязка в `apps/api/src/common/rate-limit.ts`) — на регистрации, восстановлении пароля и гео-прокси; у входа отдельная нарастающая блокировка по почте и по адресу обращения. Счёт идёт по адресу, поэтому `trust proxy` в `configure-app.ts` обязателен.
- **Заголовки безопасности** отдаёт фронт (`apps/web/next.config.ts`): CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `HSTS`. Узлы карт перечислены одним списком `MAP_HOSTS` и подставляются в CSP оттуда; сторож — `apps/web/src/test/security-headers.test.ts`.
- **Проверка источника** на изменяющих методах (`apps/api/src/common/origin-check.ts`): список берётся из `SPORT_HUB_ALLOWED_ORIGINS`, а если его нет — из публичного адреса площадки. Пустой список не означает «пропускать любой».
- **Восстановление пароля** заложено целиком; отправка писем спрятана за интерфейсом `Mailer` с токеном внедрения (`apps/api/src/mail/mailer.ts`), реализация выбирается в `storage.module.ts`. Токены восстановления живут в отдельной таблице и хранятся хешами.
- **Уборка просроченных сессий** — `npm run db:sessions:prune`.

### Развёртывание и ограничения

- **Контейнеры на своей машине (VPS)** — принятый способ доставки. Три сервиса: база, бэкенд, фронт. Описание — `docker-compose.yml`, образы — `docker/api.Dockerfile` и `docker/web.Dockerfile`, порядок выкатки — `docker/PRODUCTION.md`.
- **Профили compose**: без профиля поднимается только база; `--profile app` — всё приложение; `--profile migrate` — разовый накат миграций из ступени `builder`. На боевом сервере миграции накатываются рабочим образом с подмонтированными схемой и настройками (`docker/PRODUCTION.md`, раздел 5).
- **Порядок при изменении схемы: сначала миграция, потом код.** Аддитивная миграция безопасна для ещё работающего старого кода; обратный порядок даёт окно, в котором новый код обращается к колонкам, которых ещё нет.
- **Запуск на сервере держит сам Docker**: у всех сервисов `restart: unless-stopped`. pm2 не используется — иначе после перезагрузки два способа запуска поделили бы между собой порты 3000 и 3001. nginx проксирует на `127.0.0.1:3000`, и контейнер фронта публикует ровно этот адрес.
- **Откат — восстановление базы из дампа**, порядок в `docker/PRODUCTION.md`, §8. Дамп снимается **до** выкатки.
- **Vercel не подходит**: бэкенд NestJS — отдельный долгоживущий процесс, а не набор функций.
- ⚠️ **Платформа сборки.** Машина разработки на ARM, сервер на x86. Нативные модули собираются под конкретную платформу и на чужой не запускаются, поэтому образы для сервера собираются командой `npm run images:build:server` (`--platform linux/amd64`) либо прямо на сервере.

⚠️ Одно имя `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` живёт в двух местах и ведёт себя по-разному:
на бэкенде это обычная серверная переменная, во фронте префикс `NEXT_PUBLIC_` заставляет Next
подставить значение прямо в клиентский бандл на сборке. Рантайм-переменной такое значение
не подменить — образ надо пересобирать. Серверный ключ геокодера поэтому вынесен в отдельное
имя `YANDEX_GEOCODER_API_KEY`; пока оно не задано, геокодер работает на общем ключе карт.

⚠️ Второе имя с двойным поведением — `SPORT_HUB_API_ORIGIN`. Next вычисляет правила
проксирования во время сборки и записывает готовый адрес назначения в манифест маршрутов,
поэтому для прокси `/api/*` это переменная сборки. Отрисовка страниц на сервере читает ту же
переменную при запуске. Значит задавать её надо в обоих местах, а смена адреса бэкенда требует
пересборки образа фронта. Проверить, что уехало в сборку:
`grep -o 'http://[^"]*' apps/web/.next/routes-manifest.json`.

⚠️ Файлы окружения в образ не копируются. Слой образа неизменяем: вычистить из него ключ потом
нельзя, только пересобрать образ и отозвать ключ.

### Внешние интеграции

- **Яндекс.Карты 3.0 (JS API)** — живая карта с маркерами, ключ `NEXT_PUBLIC_YANDEX_MAPS_API_KEY`. Тёмная тема — CSS-фильтр `grayscale(1) invert(1)` на `canvas` YMaps3, переключатель `MapThemeToggle` с persist через `useMapThemeStore`.
- **Яндекс.Geocoder (HTTP API)** — серверный прокси `POST /api/geocode`, ключ `YANDEX_GEOCODER_API_KEY` (при отсутствии — общий ключ карт). Обращение идёт с тайм-аутом.
- **Яндекс.Geosuggest (HTTP API)** — серверный прокси `POST /api/suggest`, клиентский хук `useSuggest`, ключ `YANDEX_SUGGEST_API_KEY`. Используется в `CitySuggestInput` и `AddressGeocoder` publish-модалок. Лимит 1000 запросов/сутки на MVP.
- **Почта** — за интерфейсом `Mailer`; настоящая служба пока не подключена, письма уходят в журнал.

## Адаптивность и брейкпоинты

Проект верстается mobile-first: сначала базовые стили для телефонов, затем усиление для больших экранов.

| Alias | Min width | Назначение |
| ----- | --------- | ---------- |
| `sm` | `480px` | Большие телефоны |
| `md` | `768px` | Планшеты |
| `lg` | `1024px` | Маленькие ноутбуки и landscape-планшеты |
| `xl` | `1280px` | Десктопы |
| `xxl` | `1440px` | Большие десктопы |
| `2k` | `1920px` | FullHD+ |

- Кастомные `sm` (480, перекрывает дефолтные 640), `xxl` (1440) и `2k` (1920) задаются через `@theme` в `globals.css`; `md`, `lg`, `xl` — дефолтные Tailwind.
- Контейнер главной + Header + админ-панели + detail-страниц (`/clubs/[slug]`, `/trainers/[slug]`) + Footer — `max-w-[1440px]` (потолок), выше 1440 — симметричные пустые поля. Остальные страницы (ЛК-подмаршруты, `/booking/[scheduleId]`) — `max-w-7xl` (1280), портируются по мере rebrand'а.
- Лишние брейкпоинты не добавляем, если компоненту они не нужны.
- На root-контейнере страницы — `overflow-x-hidden` для защиты от случайного horizontal scroll.

## Соглашения по коду

- **Главное правило:** ⭐ всё, что пишем, должно быть масштабируемым, расширяемым, улучшаемым и легко модернизируемым — включая архитектуру БД. Формулировка — в `CLAUDE.md`, чек-лист проверки — выше в этом файле («Главное правило — проекция на наш стек»). При конфликте «быстрее» против «расширяемо» выигрывает «расширяемо».
- **Язык кода:** TypeScript, строгий режим
- **Комментарии:** на русском
- **Компоненты:** Server Components по умолчанию, `"use client"` только при интерактивности
- **Стили:** Tailwind CSS классы в JSX
- **Адаптивность:** все экраны и компоненты mobile-first
- **Импорты:** через алиас `@/`
- **Работа с данными:** фронт за данными ходит только по HTTP. Страницы — через `apps/web/src/lib/server-api.ts`, браузер — обычным `fetch('/api/...')`. Прямое чтение данных из `apps/web` запрещено и стережётся тестом `architecture.test.ts`.
- **Личность:** только из серверной сессии. Идентификатор пользователя не принимается ни в теле, ни в строке запроса — стережёт `identity-boundary.test.ts`.
- **Слои бэкенда:** контроллер разбирает запрос и задаёт форму ответа, сервис держит правила, репозиторий отвечает за одну коллекцию. Контроллер не пишет SQL, репозиторий не знает про HTTP.
- **Zustand:** только для клиентского состояния (фильтры, UI-state, уведомления, тема карты). Серверные данные в Zustand не кладём — страницы получают их с бэкенда
- **Заглушки:** помечаем `// STUB:`
- **API ответы:** `{ success: true, data: ... }` или `{ success: false, error: "..." }`. Форму собирает общий перехватчик `apps/api/src/common/api-response.interceptor.ts`; контроллер возвращает данные и выражает нужную форму типом. Три отклонения от общего правила сохранены ради совместимости с фронтом: ответ без `data`, счётчики рядом с `data` (журнал, публикации) и счётчики внутри `data` (уведомления).
- **Ошибки:** контроллеры и сервисы бросают доменные ошибки (`apps/api/src/common/domain-error.ts`), код ответа выбирается по типу ошибки. Тексты ошибок — часть контракта: они закреплены сторожем `apps/api/src/common/error-messages.test.ts` и сверкой контрактов.
- **Принцип разработки:** `Данные -> API -> UI`
- **Дизайн-токены:** в JSX используем `var(--ui-*)` (через arbitrary-values Tailwind: `bg-[var(--ui-card)]`) или `--color-*`/`--font-*` алиасы. Hex-коды напрямую запрещены.
