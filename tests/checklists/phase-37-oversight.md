# E2E: Phase 37 — надзорная лента администратора

**Роли:** администратор, **второй** администратор, человек, гость — личность меняется
по ходу, каждая смена оформлена отдельным шагом
**Base URL:** http://localhost:3000
**Инструмент:** Playwright MCP по правилам `.claude/skills/e2e-playwright/SKILL.md`

## Учётные записи

| Кто                           | Откуда берётся                                                | Как входит                                       |
| ----------------------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| Владелец, посторонний, клиент | `scripts/e2e-fixture.mjs`, `E2E_USERS`; пароль `E2E_PASSWORD` | `POST /api/auth/login`                           |
| Администратор                 | живой `admin@sporthub.local`                                  | `POST /api/auth/login` **с `portal: 'service'`** |
| **Второй администратор**      | заводится прогоном, см. предупреждение ниже                   | то же                                            |
| Гость                         | сессии нет                                                    | `POST /api/auth/logout` перед шагом              |

⚠️ **Второй администратор обязателен.** Сценарии 1 и 2 — про общую очередь, и без
второй служебной записи они проверяют пустоту. Фикстура служебных записей не заводит
(решение фазы 36). Способ появления определяется на шаге 37.2 и **обязан убирать
за собой**: лишняя служебная запись в живой базе — это дыра доступа, а не мусор.

⚠️ **Уборка прогона не снесёт надзорные строки.** У них нет `user_id`, а живой
`admin@sporthub.local` не помечен признаком прогона. Убирать явно — иначе вкладка
администратора будет копить мусор прогонов, ровно как копились публикации до фазы 36.

## Предусловия

- `npm run app:up`, база мигрирована, свой `E2E_RUN_TAG`
- `seedRunUsers()` завёл людей прогона
- прогон завёл **своими** данными: клуб с расписанием, карточку тренера, живую будущую
  запись клиента, связь тренера с клубом
- ⚠️ **Живые публикации не трогаем.** Сценарии скрывают, стирают каскадом и разрывают
  связи — на живых данных это необратимо

⚠️ **Шаг не засчитывается по коду ответа.** 200 без проверки того, что на экране, —
не пройденный шаг. Фаза целиком про то, что сервер и браузер расходятся.

⚠️ **Один контекст на сессию.** «Гостем» — это после `POST /api/auth/logout`, а не
в новом окне. После каждого входа обязателен `browser_navigate`: страница, открытая
до входа, всё ещё гостевая.

⚠️ **Проверки «в базе» делает прогон, а не браузер.** `browser_evaluate` выполняет JS
в контексте страницы: он умеет только `fetch` к API и не имеет соединения с PostgreSQL.
Всё, что начинается со слов «в базе», проверяется хелпером `readDb()` прогона
`tests/e2e-phase-37-run.mjs` — по образцу `e2e-phase-36-run.mjs`. Шаги ниже, помеченные
`readDb`, выполняются вне браузера.

⚠️ **Массовый засев — тоже работа прогона.** Сценарий 7 требует 150 надзорных строк;
заводить их действиями через интерфейс непрактично, а маршрута массового создания
в продукте нет и не будет. Строки кладёт прогон напрямую, тем же признаком `E2E_RUN_TAG`,
и он же их убирает.

## Scenario 1: очередь общая

- [ ] **step-1** Вход администратором, `browser_navigate` на `/service-portal/notifications`
- [ ] **step-2** Снять число неразобранных в значке и в ленте — **эталон**

      меню совпадает
- [ ] **step-5** Выход, вход **вторым** администратором, `browser_navigate` на ленту

      (вне браузера — у страницы нет соединения с базой)

## Scenario 2: разобрал один — видно всем

- [ ] **step-10** Переключить отбор на «разобрано» — строка на месте, **подпись
      называет второго администратора**
- [ ] **step-11** Выход, вход первым администратором, `browser_navigate` на ленту
- [ ] **step-12** Assert: у первого строка **тоже** разобрана, значок такой же
- [ ] **step-12a** «Отметить все» → Assert: **спрашивает подтверждение**; отмена

- [ ] **step-12c** «Вернуть в очередь» на разобранной строке. Assert: строка снова

- [ ] **step-14** Assert: в журнале (`/service-portal/logs`) строка события **на месте** —

⛔ **Раздел «Надзор» не открывается ни у кого.** `/service-portal/notifications`
отдаёт «Сервис временно недоступен»: `SUPERVISION_PAGE_SIZE` объявлена в модуле
с `'use client'`, серверная страница импортирует её в `limit`, через границу
клиент/сервер приезжает заглушка, её текст уезжает в строку запроса, API отвечает 400. Сорок шагов чек-листа спрашивают именно эту страницу.

Самостоятельных находок, не считая блокера, — три: отметка надзорной строки человеком
отвечает 404 вместо 403 (step-55), удаление — 200 с `deleted: 0` вместо 403 (step-56),
реестр планов уборки собирает `DELETE FROM undefined` (step-61). Ещё три дефекта
видны по данным, хотя их шаги закрыты блокером: строка про стёртую запись не называет
человека (step-21), из строк про запись и связь перехода в панели нет вовсе
(step-35, step-36), сценарий 4 невыполним по построению общей очереди.
