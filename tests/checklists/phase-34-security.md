# E2E: Phase 34 — авторизация и безопасность

**Role:** cross-face (гость → человек без лиц → владелец карточки → владелец клубов → владелец обоих → админ)
**Base URL:** http://localhost:3000
**Прогон:** Playwright MCP по правилам `.claude/skills/e2e-playwright/SKILL.md`.
Отчёт — в `tests/reports/`.

**Preconditions:**

- PostgreSQL поднят (`npm run db:up`), миграции применены, включая таблицу `sessions`.
- Данные засеяны единым набором учёток. ⚠️ **Ролей больше нет (фаза 35):** сид даёт
  по человеку на каждый **набор лиц услуг** — id=1 `admin@sporthub.local` (служебная
  запись, `accountKind: 'admin'`), id=2 `owner@sporthub.local` (клубы 1 и 2),
  id=3 `trainer@sporthub.local` (карточка тренера 1), id=4 `athlete@sporthub.local`
  (лиц нет), id=5 `both@sporthub.local` (клуб 3 **и** карточка тренера 2).
  Общий пароль — константа `DEV_PASSWORD` в `dev-seed.ts`.
- Подняты оба процесса: бэкенд `:3001`, фронт `:3000`.
- В расписании есть будущий слот со свободными местами и хотя бы одна **завершённая**
  запись человека — она нужна сценариям отзыва.
- Браузер стартует без cookie: сессии предыдущих прогонов не переносятся.

⚠️ **Правило прогона.** Урок Ф33: шаг не засчитывается по коду ответа. `200` вместо `401` —
это и есть дефект фазы. Каждый шаг проверяет **содержимое**: что именно вернулось, что видно
на экране, что записано в журнал.

- [x] **step-72** id=3 подтверждает запись на **своё** занятие — 200, статус `confirmed`.
- [x] **step-73** id=3 подтверждает запись на занятие **чужого клуба** — 403, текст
      «Недостаточно прав для подтверждения записи». Assert: текст именно этот — остановило
      владение слотом.
- [x] **step-73a** id=2 подтверждает **свою собственную** запись в свой клуб — 403
      «Решение по своей записи принимает вторая сторона». ⚠️ Записаться в свой зал

- [x] **step-74** Связь тренер↔клуб. ⚠️ Пара берётся **свободная**: у пары «тренер 1 ↔ клуб 1»
      подтверждённая связь уже есть в сиде, и создание даст 409, а не проверку прав.

      ЧУЖУЮ сторону (клуб шлёт заявку с `initiatedBy=trainer` по чужому тренеру) — 403
      «Недостаточно прав для отправки запроса»; assert: связь не создана.
- [x] **step-74a** **Решение 22 — единственное исключение.** Под id=5 связать свой клуб 3
      со своей карточкой 2: `POST /api/trainer-club-links` → 201 и статус **сразу**
      `confirmed`, без `pending` и без уведомлений. Assert: обе стороны принадлежат одной
      учётной записи — спрашивать не у кого; проверка «названная сторона моя» из step-74
      при этом остаётся на месте и закрывает подмену чужой стороны.
- [x] **step-75** Assert: набор разделов кабинета выводится из **лица, чей это кабинет**
      (сравнивать списками, а не на глаз) — в `/profile/trainer/1/*` у id=3 «Моя карточка»,
      в `/profile/club/1/*` у id=2 «Публикации», а у id=5 **два кабинета**:
      `/profile/club/3/*` с «Публикациями» и `/profile/trainer/2/*` с «Моей карточкой».
      Пятый случай прежняя модель выразить не могла вовсе.
      ⚠️ Разделы зависят не только от лица, но и от **данных**: «Бронирования», «Клиенты»
      и «Статистика» появляются при наличии записей **у этого лица**
      (`FACE_BOOKING_SECTIONS` в `apps/web/src/components/profile/profile-nav-items.ts`).
      «Связи», «Отзывы», «Финансы», «Уведомления», «Настройки» есть у лица **всегда** —
      условие «а есть ли публикация» снято шагом 35.33: в кабинет лица нельзя попасть,
      не владея им. Чтобы сравнение говорило о владении, у сравниваемых лиц должны быть
      записи — или не быть ни у одного.
