## Дефект приложения: значок колокольчика на странице ленты кабинета

⚠️ **Найден этим прогоном, воспроизводится.**

✅ **Дописано 13.09.2026: починен шагом 37.75.** У поля «непрочитано» было два писателя
с разным смыслом — лента кабинета знает ящик ОТКРЫТОГО кабинета, опрос колокольчика
считает ВСЕ ящики человека, и побеждал тот, кто записывал последним. Теперь у числа
один хозяин. Тест — `apps/web/src/test/stores/useNotificationsStore.test.ts`.
Живым браузером правка проверена перепрогоном 13.09.2026 на пересобранном стенде
(шаг 37.78, отчёт `phase-37-browser-2026-09-13.md`): значок, лента и пункт меню
сверяются между собой на каждом шаге счётчиков.

**Что ждали.** Колокольчик человека обещает считать **все его ящики сразу** —
так сказано в самом `NotificationBell` («у человека ящик НЕ называется вовсе»),
и так ведёт себя выпадашка: она показывает строки по всем лицам.

**Что получили.** На `/profile/me/notifications` значок **иногда** показывает
число ОТКРЫТОГО ящика вместо числа человека. Замер восемью загрузками подряд
при нуле непрочитанных в личном ящике и трёх в ящике лица:

```
значок на /profile/me/notifications: 3 0 0 3 3 3 3 3
значок на /profile/me/dashboard   : 3 3 3 3 3 3 3 3
```

То есть на сводке кабинета — верные 3 во всех восьми заходах, на странице ленты —
ноль в двух из восьми. В самом прогоне это дало ровно то же: первый заход 12.09
увидел 0 при шести непрочитанных (шаги 30 и 51 покраснели), следующий — верные 6.

**Где.** `apps/web/src/components/profile/notifications/NotificationsListPage.tsx`
и `apps/web/src/components/layout/NotificationBell.tsx` пишут и читают ОДНО поле
`unreadCount` в `apps/web/src/stores/useNotificationsStore.ts`:

- страница на монтировании зовёт `showRows(initialFeed.items, initialFeed.unreadCount)`
  и кладёт туда число **открытого ящика** (личный — 0);
- `useUnreadCountPolling` в колокольчике кладёт туда число **человека** (все ящики — 3).

Оба писателя срабатывают на одном монтировании, и кто ляжет последним, решает
гонка ответов. Значок при этом ещё и противоречит собственной выпадашке: в кружке
ноль, в списке под ним — три непрочитанных строки.

**Цена.** Владелец лица видит «непрочитанных нет» ровно на той странице, куда
пришёл читать уведомления. Не утечка, не потеря данных — но счётчик, который
врёт через раз, перестают читать вовсе.

**Как прогон с этим живёт.** Шаги 30 и 51 снимают значок на сводке кабинета
(`/profile/me/dashboard`), где писатель один: их вопрос — «не вырос ли значок
человека от НАДЗОРНЫХ событий», и мерить им чужую гонку значило бы получать
случайный ответ на верный вопрос. Причина переезда названа комментарием в прогоне.

Прогон к переезду подписи подготовлен заранее: кнопка колокольчика ищется

## Уборка

После каждого из двух зелёных заходов:

```
Уборка стёртых предметов: club:… booking:… club:…
Уборка: людей 4, клубов 2, карточек 1
Добор не понадобился: реестр планов унёс все надзорные строки прогона.
✅ step-62 — людей 0, служебных 0, надзорных 0/0
```

Второй администратор заводится прогоном прямо в базе (маршрута создания служебной
записи в продукте нет) и убирается там же — лишняя служебная запись в живой базе
это дыра доступа, а не мусор. Живые публикации не тронуты: всё, что скрывалось,
стиралось и разрывалось, заведено прогоном.

⚠️ **Побочное действие, названное вслух.** Прогон опустошает надзорную очередь
целиком — этого требует сам чек-лист (step-13: «Assert: лента очистилась»).
Четыре надзорные строки, лежавшие в живой базе от прошлой сессии, им снесены.
