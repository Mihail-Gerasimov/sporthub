## Как прогон шёл: два захода

Чек-лист прогонялся дважды по два раза: сперва по коду, каким он был днём 11.09,
потом — по коду с закрытыми находками. Первый заход и есть главная ценность
этого прогона, поэтому он здесь не стёрт.

### Заход I (до починки): 24 из 67

**Сорок падений из сорока трёх — один дефект.**

`/service-portal/notifications` отдавал экран **«Сервис временно недоступен»**,
код обращения `2895829738`. Не «очередь пуста», не «недостаточно прав» — страница
не собиралась вовсе. Лог контейнера `sporthub_web` называл причину дословно:

```
Error [BackendUnavailableError]: Бэкенд ответил кодом 400 на запрос
/notifications?unreadOnly=true&offset=0&limit=function%28%29%7Bthrow+Error%28%22Attempted+to+call+
SUPERVISION_PAGE_SIZE%28%29+from+the+server+but+SUPERVISION_PAGE_SIZE+is+on+the+client…
```

`SUPERVISION_PAGE_SIZE` была объявлена в модуле с `'use client'`, а серверная
страница импортировала её в `limit`. Через границу клиент/сервер не-компонентный
экспорт клиентского модуля приезжает **клиентской ссылкой-заглушкой** — функцией,
которая при вызове бросает; `String(…)` от неё уехал в строку запроса, API ответил
400, страница упала в границу ошибки.

⚠️ **Почему не поймали ни сборка, ни тесты.** `npm run build` проходил: граница
клиент/сервер в Next проверяется в рантайме, а не типами. А
`apps/web/src/test/admin/supervision-page-request.test.tsx` — тест ПОДКЛЮЧЕНИЯ,
написанный ровно про эту страницу, — был **зелёным, 4 из 4**: он импортирует
ту же константу в окружении vitest/jsdom, где границы нет и это обычное число 15,
и сравнивает `limit` с числом, которое сам же подставил. Совпадение было
гарантировано по построению.

Это в точности тот класс дефекта, ради которого фаза и затевалась: серверная часть
написана и покрыта, а до браузера не доехала. Только не доехал весь раздел сразу.

**Ещё пять находок того же захода:**

| # | Ждали | Получили |
| --- | --- | --- |
| Д-2 | step-55: **403** («не 404») | `404 Уведомление не найдено` — отбор сужался до `userId`, и отказ выглядел как пропавшая строка |
| Д-3 | step-56: **403** («не 200 с `deleted: 0`») | `200 {"deleted":0}` — «удалять было нечего» вместо «вам нельзя» |

| Д-8 | «сирот ноль» | надзорная строка переживает свой предмет по построению, а номер стёртого вывести из таблицы уже неоткуда |

Ещё два падения оказались не дефектами кода, а **расхождением плана с самим собой**,
и закрыты правкой плана и чек-листа:

- **Сценарий 4** требовал, чтобы скрывший публикацию своей строки не видел. При
  одной строке на всех (решение 5.2) спрятать её от одного зрителя можно только
  заведя «прочитано для каждого» — то есть ту личную почту, от которой очередь
  и ушла. Утверждение снято: проверяется, что строка ОДНА, адресована очереди
  и видна обоим.
- **step-35 / step-36** требовали перехода к записи и к связи. Разделов записей,
  отзывов и связей в служебной панели нет вовсе, и мёртвая ссылка туда была бы
  хуже её отсутствия. Условие приёмки 16 переформулировано; шаги проверяют теперь,
  что строка понятна БЕЗ перехода.

## Отступления от буквы чек-листа

Названы вслух, все три — в шапке прогона.

1. **Личности разведены по отдельным браузерным контекстам.** Требование «один
   контекст на сессию» написано под ручной прогон MCP, где вкладка одна; отдельный
   контекст даёт то же строже. Для step-12d двух живых служебных сессий требует
   сам чек-лист: «почти одновременно» одной вкладкой не выражается.
2. **Вторая служебная запись заводится прямо в базе** (`account_kind = 'admin'`)
   и убирается там же: маршрута создания служебной записи в продукте нет, фикстура
   их не заводит (решение фазы 36). Уборка проверяется отдельным шагом — лишняя
   служебная запись в живой базе это дыра доступа, а не мусор.
3. **step-15, случай «скрывший неизвестен»** воспроизводится обнулением
   `hidden_by_user_id` у СВОЕЙ скрытой публикации: в продукте такое бывает только
   у строк из прошлого.

## Изоляция и уборка

Прогон заводит своих людей (`seedRunUsers`), четыре клуба, карточку тренера, две
связи и живую запись клиента; живые публикации не трогает. 150 надзорных строк
сценария 7 кладутся напрямую, но с предметами прогона — чтобы уборка их нашла.

⚠️ **Стёртые предметы прогон запоминает ДО удаления.** Надзорная строка сознательно
переживает свой предмет: событие «публикация стёрта» без публикации — единственная
его форма. Но номер стёртого потом неоткуда вывести — ни в `clubs`, ни в `bookings`
его уже нет. Поэтому прогон копит список и отдаёт его уборке параметром `subjects`
(`cleanup-publications.mjs`). В обоих прогонах это `club:… booking:… club:…`,
и добор по окну прогона после этого **не понадобился ни разу** — реестр планов
унёс всё сам.

⚠️ **У самой `cleanupRun()` параметра `subjects` нет** — заход по стёртым предметам
делает прогон отдельно, перед ней. Это не дефект, но и не самоочевидно: следующий
прогон, который что-нибудь сотрёт, обязан повторить этот заход сам, иначе строка
про стирание останется в живой базе навсегда.

**После каждого из двух прогонов:** людей прогона 0, служебных записей прогона 0,
надзорных строк 0 при 0 до прогона. `notifications` вернулись к 66 личным /
1 карточке / 2 клубным, публикаций с признаком прогона ноль.
