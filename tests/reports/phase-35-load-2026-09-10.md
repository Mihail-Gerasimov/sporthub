# Нагрузка: ящики уведомлений и список лиц (шаг 35.45)

**Дата:** 2026-09-10
**Инструмент:** k6 v1.x, профиль `mailbox` в `load/k6-scenarios.js`
**Команда:**
`k6 run -e ONLY=mailbox -e VUS=5 -e DURATION=90s -e API=http://localhost:3000 -e MAILBOX_EMAIL=marina@studio.local load/k6-scenarios.js`
**Стенд:** контейнеры `npm run app:up` из кода фазы 35, живая мигрированная база.
**Испытуемый:** `marina@studio.local` — **20 лиц услуг**, 66 личных уведомлений.
Взят намеренно: это самый тяжёлый набор на площадке.

## Что меряется

Три запроса, ровно те, что делает открытие страницы кабинета:

1. `GET /api/auth/me` — список лиц;
2. `GET /api/notifications?clubId=N` (или `trainerId=N`) — лента открытого лица;
3. `GET /api/notifications?scope=personal` — личный ящик.

Лицо выбирается по номеру итерации, а не первое: иначе весь прогон читал бы один
ящик, и попадание в кеш выдало бы себя за отзывчивость.

## Три дефекта самого замера, найденные по дороге

Ни один из них не в приложении — все три в профиле нагрузки. Записаны, потому что
каждый делал замер **зелёным и бессмысленным одновременно**.

### З-1. Профиль не читал ящики вовсе, оставаясь зелёным

Приложение ставит cookie `__Host-sh-session` с признаком `Secure`, а нагрузка идёт
по HTTP — хранилище cookie в k6 такую молча отбрасывает. `GET /api/auth/me` отвечал
401, список лиц приезжал пустым, цикл по ящикам **не выполнялся ни разу**.

Профиль при этом был зелёным: проверка смотрела `Array.isArray(faces)`, а пустой
массив — тоже массив. Ровно тот вид ложного зелёного, за которым охотится вся фаза,
только не в тестах, а в нагрузке.

**Исправлено:** cookie передаётся заголовком; проверка требует **непустого** списка лиц.

### З-2. Мерился вход, а не ящики

Первая редакция входила на каждой итерации. Ограничитель частоты (5 попыток на пару
«адрес + почта», дальше нарастающая блокировка) отбивал 19.79% запросов — то есть
пятая часть замера была замером ограничителя. В жизни человек входит один раз
и дальше работает сессией.

**Исправлено:** вход перенесён в `setup()` — один на весь прогон.

### З-3. Доля ошибок не замечала оборванных соединений

`error_rate` считал провалом только `status >= 400`. k6 отдаёт оборванным запросам
`status === 0`, и они проходили мимо: сводка показывала **0.00% ошибок при 16%
оборванных запросов** в разделе HTTP. Замер выглядел безупречным ровно там, где
сервер переставал отвечать.

**Исправлено:** отказ соединения считается отказом. После правки обе цифры сходятся.

## Дефект приложения, найденный нагрузкой

### Д-2. Лента уведомлений без `limit` отдавалась целиком

Потолок в сто строк существовал, но применялся только к **заданному** лимиту.
Клиент, не назвавший его, получал ленту **целиком**: постраничность была написана
и работала — просто по умолчанию выключена.

Цена запроса росла вместе с историей человека: у испытуемого 66 уведомлений давали
12 КБ на каждое открытие кабинета; за год активной жизни это мегабайты. Прямое
нарушение главного правила — «постраничность в запросе к БД».

**Исправлено:** умолчание равно потолку. Общее число едет рядом (`total`) — дочитать
остальное есть чем. Закреплено четырьмя тестами в `notifications.controller.test.ts`
на наборе из 150 строк: без лимита отдаётся 100, `total` равен 150, лимит больше
потолка срезается, лимит меньше соблюдается.

## Предел стенда

При 10 виртуальных пользователях появляются 5.11% оборванных соединений, при 40 —
15–16%. Порог в замер не входит: это предел dev-контейнеров на ноутбуке, а не
приложения — задержка при этом остаётся в пределах 13 мс. Насыщение наступает
около **1000 запросов/с** независимо от числа пользователей.

Замер снят на 5 пользователях — там стенд отвечает без единого отказа и выдаёт
те же 975 запросов/с.
