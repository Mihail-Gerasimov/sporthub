# Нагрузочный замер фазы 33

**Дата:** 20.08.2026
**Что меряли:** три профиля ОДНОВРЕМЕННО (атлет, провайдер, админ) + отдельный профиль гонки.
**Где:** машина разработки, ARM, 12 ядер, 8 ГБ памяти. База — PostgreSQL 16 в контейнере.
**Данные:** боевой срез, перенесённый скриптом (415 строк).
**Чем:** `k6 run load/k6-scenarios.js`.

⚠️ Это замер на машине разработки, а не на боевом сервере. Числа отвечают на вопрос
«что упрётся первым», а не «сколько выдержит прод»: у прода два ядра против двенадцати.

---

## Три профиля одновременно

30 виртуальных пользователей (24 атлета, 5 провайдеров, 2 админа), 45 секунд.

| Метрика | Значение | Порог | Итог |
| --- | --- | --- | --- |
| Запросов всего | 101 266 (2249 в секунду) | — | — |
| Доля ошибок | **0.00%** (0 из 101 266) | < 1% | ✅ |
| Атлет, p95 | **29.5 мс** | < 1500 мс | ✅ |
| Провайдер, p95 | **27.2 мс** | < 2000 мс | ✅ |
| Админ, p95 | **27.6 мс** | < 3000 мс | ✅ |
| Медиана по всем запросам | 11.1 мс | — | — |
| Максимум | 48.7 мс | — | — |

Повторный прогон на 30 секундах дал те же числа (64 924 запроса, p95 28–30 мс, 0% ошибок) —
результат воспроизводим, а не случаен.

**Что это означает.** Ни один из профилей не упирается: самый дорогой запрос — сводка админа
и журнал — укладывается в 28 мс на девяноста пяти процентах обращений. Полного перебора
на горячих путях не осталось: отбор, порядок и постраничность ушли в запрос, под каждый
фильтр есть индекс.

## Гонка за последним местом

Профиль проверяет не скорость, а корректность: несколько участников одновременно
записываются на слот с ОДНИМ свободным местом.

| Метрика | Значение | Ожидание | Итог |
| --- | --- | --- | --- |
| Успешных записей | **1** | ровно 1 | ✅ |
| Отбито «Свободных мест нет» | 3 | остальные | ✅ |
| Неожиданных отказов | **0** | 0 | ✅ |
| Счётчик слота после прогона | 1 из 1 | не больше вместимости | ✅ |
| Строк записей на слот | 1 | 1 | ✅ |

На уровне репозитория тот же сценарий прогоняется десятью одновременными запросами
(`apps/api/src/test/concurrency.test.ts`) — результат тот же: ровно один успех.

**До фазы этот сценарий давал овербукинг.** Счётчик менялся чтением-проверкой-записью,
и между чтением и записью помещался чужой запрос.

### После настройки памяти базы и переезда в контейнеры

Замер повторён на полном контуре: база, бэкенд и фронт — все три в контейнерах,
настройки памяти базы заданы явно.

| Контейнер | Память |
| --- | --- |
| `sporthub_web` | 170 МБ |
| `sporthub_api` | 189 МБ |
| `sporthub_postgres` | 350 МБ |
| **Всего** | **709 МБ** |

Для сравнения: до фазы два процесса под pm2 занимали около 600 МБ, и базы среди них не было.
Прибавка — примерно 110 МБ на всё, включая саму базу. В два гигабайта боевого сервера
контур помещается с запасом.

Настройки, которыми это получено (`docker-compose.yml`): `shared_buffers = 256MB`,
`effective_cache_size = 768MB`, `work_mem = 8MB`, `max_connections = 30`.

⚠️ **Полтора гигабайта у базы до настройки — не то, чем кажется, но и не то, что можно игнорировать.**
Бо́льшая часть этой цифры — страничный кэш, который контейнер учитывает как свою память.
Собственные настройки при этом стоят по умолчанию и рассчитаны на машину с восемью
гигабайтами: `shared_buffers = 160 МБ`, `effective_cache_size = 5 ГБ`, `max_connections = 100`.

На боевом сервере с двумя гигабайтами эти значения завышены втрое. Перед выкаткой их надо
задать явно: `shared_buffers` порядка 256 МБ, `effective_cache_size` порядка 768 МБ,
`max_connections` по размеру пула приложения (сейчас `DATABASE_POOL_SIZE = 10`), а не сто.
Без этого база и приложение вместе упрутся в потолок памяти — и упрутся не на замере,
а на живой нагрузке.

## Что осталось за рамками замера

- **На боевом сервере замер не гоняется никогда** — он создаёт настоящие записи и меняет
  статусы. Числа для прода снимаются иначе: наблюдением за реальной нагрузкой.
- Сравнение «до и после» по абсолютным числам невозможно: прежняя реализация читала файлы
  и на 2200 запросах в секунду просто не работала бы. Сравнимо другое — поведение под гонкой:
  было «оба получили место», стало «ровно один».

## Как повторить

```bash
npm run db:up && npm run db:import
npm run start --workspace @sporthub/api
k6 run -e VUS=30 -e DURATION=45s -e ONLY=profiles load/k6-scenarios.js
k6 run -e ONLY=race -e RACE_SCHEDULE_ID=<слот с одним свободным местом> load/k6-scenarios.js
docker stats --no-stream --format '{{.Name}} {{.MemUsage}}'
```
