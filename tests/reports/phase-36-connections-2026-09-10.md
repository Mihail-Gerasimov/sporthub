# Замер: почему прогон тестов мигал и что изменилось

**Дата:** 2026-09-10
**Шаги:** 36.27, 36.28, 36.29
**Стенд:** контейнеры `npm run app:up`, тестовая база `sporthub_test`

## Диагноз при постановке задачи был неверен

Долг фазы 35 записан так: «наборы делят одну тестовую схему, и при неудачном
чередовании сосед видит чужой засев».

**Это не так.** В Vitest 4 `VITEST_WORKER_ID` — сквозной счётчик по спекам, а не номер
процесса, поэтому имя `test_${VITEST_WORKER_ID}` даёт **схему на файл**. Замер: полный
прогон создаёт 48 схем по числу файлов, трогающих базу. Изоляция была на месте всё это
время; комментарий `db-harness.ts` описывал поведение Vitest 3 и пережил переезд версии
незамеченным.

## Настоящая причина

`sorry, too many clients already`.

| Потребитель                                                      | Соединений |
| ---------------------------------------------------------------- | ---------- |
| Пул приложения в тесте (`DATABASE_POOL_SIZE` из `apps/api/.env`) | 10         |
| Пул обвязки — **второй** пул к той же базе                       | 2          |
| Исполнителей одновременно (`maxWorkers`)                         | 2          |
| **Пик прогона**                                                  | **24**     |
| Контейнеры приложения                                            | ~7         |
| `max_connections`                                                | **30**     |

Запас — отрицательный, стоило кому-нибудь открыть psql. Всплеск даёт не засев,
а `Promise.all` в самих маршрутах: один запрос разворачивает пул с одного соединения
до потолка. Поэтому падал «один случайный тест» и всегда в тяжёлом наборе.

## Что сделано

1. **Обвязка больше не держит второго пула.** Приложение поднимается первым, и обвязка
   работает его же клиентом: `TRUNCATE` и чтение среза не стоят отдельного пула.
2. **Размер пула в тестах задан явно** — `TEST_CONNECTION_BUDGET` в `db-harness.ts`,
   применяется в `setup.ts` до загрузки модулей приложения. Прежде бралось боевое
   значение 10 из `.env`, которое никто не выбирал для тестов.
3. **Потолок локального стенда посчитан отдельно от боевого.** 30 — расчёт для боевого
   сервера, где прогонов нет. Локально приложение и прогон работают одновременно;
   локальный стенд поднимается с `POSTGRES_MAX_CONNECTIONS=60`, боевой остаётся на 30.
4. **Сторож** `connection-budget.test.ts`: бюджет объявлен, посчитан и сверяется
   с фактическим размером пула. Число, живущее только в комментарии, разъезжается молча —
   именно это и произошло с описанием схем.

## Пороги: до и после

Занимаем N соединений извне и гоняем два самых тяжёлых набора
(`clubs.controller.test.ts`, `publication.service.test.ts`).

| Потолок | Пул прогона              | Занято извне | Итог                                                               |
| ------- | ------------------------ | ------------ | ------------------------------------------------------------------ |
| 30      | 12 на файл (два пула)    | 18           | ❌ падает                                                          |
| 30      | 4 на файл (один пул)     | 22           | ❌ падает — **одного сужения пула мало**: контейнеры держат ещё ~7 |
| **60**  | **4 на файл (один пул)** | 22           | ✅ проходит                                                        |
| **60**  | **4 на файл (один пул)** | 24           | ✅ проходит, 92 из 92                                              |
| **60**  | **4 на файл (один пул)** | 40           | ✅ проходит, 92 из 92                                              |
| **60**  | **4 на файл (один пул)** | 46           | ✅ проходит, 64 из 64                                              |

**Порог сдвинулся с 18 до 46 и более.** Разница порогов — доказательство; «вроде больше
не падает» доказательством не является.

⚠️ **Важное наблюдение, стоившее отдельного замера.** Сужение пула само по себе
проблему не закрыло: при 22 занятых прогон падал и с пулом 4. Число слотов базы —
такой же посчитанный ресурс, как и размер пула, и считать надо оба. Если бы замер
остановился на первом шаге, починка выглядела бы сделанной и не была бы ею.
