## Phase 13: Provider Publish Modals UI (MVP shell) ✅ ЗАВЕРШЕНА

> После этой фазы: в `/profile/provider` вместо текущих заглушек открываются 2 полноценные MVP-модалки: публикация клуба и публикация тренера.

На этом этапе модалки ещё ничего не сохраняют в JSON и не запускают реальный create-flow.
Задача фазы — собрать полный UI-каркас, секции, поля, UX открытия/закрытия, базовую валидацию и stub-поведение для будущих функций.
Все данные в модалках пока работают как `preview / UI-only` сценарий.
Текущая provider-страница и быстрые действия уже существуют, поэтому Phase 13 расширяет готовый кабинет, а не создаёт его заново.

**Ключевые решения:**

- Используется существующий modal-pattern проекта на базе `src/components/ui/Modal.tsx`, без второй параллельной реализации модалок.
- Обе модалки работают как `UI-only / preview-only` сценарий.
- Состояние модалок и форм хранится локально в client-компонентах; на этой фазе не добавляется отдельный store.
- `db.ts`, API routes и `src/data/*.json` на этой фазе не меняются.
- На этой фазе не изменяются доменные типы (`Club`, `Trainer`, `Offering`, `Schedule`) ради form-only полей модалок.
- Все дополнительные поля UI-оболочки, которые пока не участвуют в реальном create-flow, остаются локальными form-only значениями.
- Primary action в footer не сохраняет данные: после прохождения базовой валидации пользователь получает честное уведомление, что сохранение публикации будет доступно в следующей фазе.
- Future-поля визуально видимы, но не участвуют в submit-flow.
- Для stub-уведомлений используется единый notice-pattern проекта.

**Тактические заметки к реализации:**

1. **Step 13.1** — создать минимальные заглушки `PublishClubModal` и `PublishTrainerModal` (пустые компоненты с минимальным UI), чтобы импорты работали и тесты проходили. Без этого шаг не закроется по верификации.
2. **Step 13.3 / 13.4** — stub-поля рендерить сразу в составе секций (визуально с пометкой «скоро»), а в Step 13.8 только навесить единый notice-pattern и disabled-state. Иначе в 13.8 придётся переделывать разметку.
3. **Step 13.5 (валидация)** — перед реализацией проверить текущий `Modal.tsx` на поддержку scroll (`max-h` + `overflow-y-auto`). Если нет — добавить, иначе ошибки валидации внизу длинной формы будут невидимы на мобильных.
4. **Step 13.6 (фото-stub)** — шаг маленький. Объединить в одну итерацию с 13.5 или 13.7, чтобы не тратить целый цикл верификации на 10 строк кода.
5. **Step 13.7 (расписание)** — самый тяжёлый UI-шаг фазы. Держать отдельно, не комбинировать с другими.
6. **Steps 13.9 + 13.10** — делать в одну итерацию: 13.9 — ручная проверка, 13.10 — документация. Оба без нового кода.

### Step 13.5: Добавить базовую client-side валидацию publish-форм

- **Действие:** Для обеих модалок добавить минимальную валидацию обязательных MVP-полей.
- На этой фазе не делать тяжёлую доменную валидацию и не подключать серверные схемы.
- Нужен только понятный MVP-уровень:
  - пустое обязательное поле показывает локальную ошибку;
  - email проверяется по базовому формату;
  - числовые поля не должны быть пустыми или отрицательными;
  - нельзя пройти submit-flow без обязательного минимума;
  - минимум 1 направление / специализация / слот обязателен.
- Ошибки отображаются прямо в форме в понятном русском виде.

- На этой фазе не добавлять сложную cross-field валидацию доменного уровня:
  - не проверять пересечения слотов между собой;
  - не проверять конфликт расписания с существующими сущностями;
  - не проверять уникальность названий;
  - не валидировать будущие/stub-поля.
- Для времени достаточно базовой проверки:
  - время начала и окончания заполнены;
  - окончание позже начала.

**Проверка:**

- при пустых обязательных полях пользователь видит ошибки;
- ошибки исчезают после корректного ввода;
- future-поля не валидируются и не блокируют форму.

**Ожидаемый результат:**

- модалки ощущаются как живые формы, а не как декоративный UI.

**Тесты:**

- пустой submit показывает ошибки;
- валидное заполнение убирает ошибки;
- primary action недоступен или не проходит до соблюдения обязательного минимума.

**Реализация:**

- **Файлы:**
  - `src/components/profile/publish-validation.ts` (~80–100 строк) — чистые функции валидации: `validateClubForm(state): Record<string, string>`, `validateTrainerForm(state): Record<string, string>`; возвращают объект ошибок `{ fieldName: 'Сообщение' }` или пустой объект
  - `src/components/profile/PublishClubModal.tsx` — добавить вызов `validateClubForm` при submit, рендер ошибок рядом с полями
  - `src/components/profile/PublishTrainerModal.tsx` — аналогично `validateTrainerForm`
  - `src/test/profile/publish-validation.test.ts` — unit-тесты чистых функций валидации
  - `src/test/profile/publish-club-modal.test.tsx` — дополнить: пустой submit → ошибки видны; валидный ввод → ошибки исчезают
  - `src/test/profile/publish-trainer-modal.test.tsx` — аналогично
- **Ключевые экспорты:**
  - `validateClubForm` (publish-validation.ts)
  - `validateTrainerForm` (publish-validation.ts)
- **Паттерны:** валидация — чистые функции без side-effects; ошибки хранятся в локальном `useState<Record<string, string>>`; перед реализацией проверить scroll в `Modal.tsx` / `PublishModalShell` — если `max-h` + `overflow-y-auto` отсутствует, добавить
- **Зависит от:** локальных типов `ClubFormState`, `TrainerFormState` из модалок

### Step 13.8: Добавить единый stub-режим для future-полей и primary action

- **Действие:** Для всех future-полей и future-действий использовать единый pattern:
  - либо `disabled-state`;
  - либо notice при клике:
    - `Функционал будет доступен в следующих обновлениях`

  - после прохождения базовой валидации пользователь может нажать `Создать публикацию`;
  - данные не сохраняются;
  - вместо сохранения показывается notice:
    - `Сохранение публикации будет доступно в следующей фазе`

- Будущие поля не должны участвовать в submit-flow.

- На этой фазе запрещён fake-success сценарий:
  - нельзя показывать сообщение в духе `Публикация создана`;
  - нельзя изменять блок `Мои публикации`;

- невозможно случайно “сохранить” несуществующий функционал;
- primary action ведёт себя честно и предсказуемо.

**Ожидаемый результат:**

- модалки выглядят полноценно, но поведение остаётся честным и контролируемым.

**Тесты:**

- future-поля не участвуют в submit-flow;

- никаких вызовов data-layer или API не происходит.
