## 1. Зачем эта фаза

⚠️ Весь этот раздел — **снимок кода на 08.09.2026, до работ фазы**. Каждая описанная в нём
дыра закрыта; перечень нужен, чтобы было видно, от чего защищались и почему решения
приняты именно такие.

Ф33 закрыла слой данных: PostgreSQL, транзакции, argon2id, атомарные счётчики, отбор в запросе.
По всем показателям приложение было готово к боевой выкатке — кроме одного.

**Сервер не знает, кто к нему пришёл, ни в одном из 64 маршрутов.** Это не оборот речи, это
результат поиска: `grep` по `UseGuards|CanActivate|APP_GUARD|AuthGuard|session|Cookie|Bearer`
по `apps/api/src` даёт два совпадения, и оба — про `SessionLevel`, уровень тренировки.

Дальше по фактам, а не по общим соображениям.

**Вход пускает без пароля.** `auth.controller.ts:68` — поле `password` объявлено в схеме (`:30`)
и не деструктурируется. Клиент его даже не отправляет: `AuthModal.tsx:304-307` кладёт в тело
только почту и тип кабинета. Сверка хеша во всём проекте вызывается **один раз** —
`users-account.controller.ts:104`, при смене пароля. Тест `auth.controller.test.ts:54` называется
«вход проходит и с неверным паролем — проверки пароля нет».

**Админом становится кто угодно.** `ServicePortalLoginForm.tsx:68-75` — форма не ходит на сервер
вовсе, `sessionUser` собирается из констант, `ADMIN_SEED_EMAIL` (`:16`) лежит в браузерном бандле.
Любая валидная почта и шесть символов пароля дают админскую сессию.

**28 маршрутов из 64 не спрашивают вообще ничего.** Среди них `GET /api/users` — почты и телефоны
всех пользователей платформы (`catalog.controller.ts:61-71`), `GET /api/logs` — весь журнал аудита
постранично (`logs.controller.ts:56-87`), `GET /api/analytics`, `GET /api/publications`,
`GET /api/users/:id/notification-preferences`.

**Ещё 3 становятся анонимными по параметру.** `?scope=all` у записей, уведомлений и заметок;
`notes.controller.ts:70-72` этим отдаёт **приватные CRM-заметки всех провайдеров обо всех
клиентах**. Чтение защищено хуже, чем запись: у POST проверка «клиент ли атлет у провайдера»
есть (`:104-120`), у GET — нет.

**36 маршрутов принимают личность на слово.** 31 из тела, 5 из query. Подставил чужой номер —
действуешь от его имени. Админские маршруты роль проверяют по базе (`access.service.ts:36-40`),
но `adminUserId` — просто число из тела: достаточно знать номер любого администратора.

**Удаление публикации не спрашивает владельца.** `clubs.controller.ts:217` и `:395` тело не читают;
`publication.service.ts:281-301` проверяет только существование. `ensureManagedBy` (`:306-315`)
зовётся исключительно из правки. В журнал при этом пишется `club?.managedByUserId ?? 0` — в аудите
удаление выглядит как действие владельца.

**Отзыв не требует посещения.** `ReviewsController` не инжектит репозиторий записей вовсе;
поиск по `canReview|hasCompletedBooking|reviewEligib` по всему проекту даёт ноль. Оценка сразу
пересчитывает публичный рейтинг в транзакции (`reviews.controller.ts:154-166`).

**Журнал аудита подделывается.** `logs.controller.ts:89-98` принимает `actorId` и `actorRole`
из тела; Zod проверяет только, что роль есть в словаре. Кто угодно пишет запись от имени админа.

**Cookie личности — голое число.** `auth-cookie.ts:23` пишет `sh-auth-user-id` через
`document.cookie`: не HttpOnly, не Secure, не подписана. Смена цифры меняет пользователя.
Бэкенд её при этом не видит вовсе — `server-api.ts:75,105` шлёт запросы без заголовков.

**Серверной защиты страниц нет ни одной.** Все проверки клиентские: 19 точек `AccessDeniedCard`
в 14 компонентах плюс один `AdminGuard`. `service-portal/(admin)/dashboard/page.tsx:22-27` грузит
всех пользователей, все записи, клубы и тренеров **до** проверки и отдаёт в RSC-поток.

Пока это стенд на своей машине — незаметно. На боевом домене это утечка персональных данных
всей платформы одним `curl` без единого заголовка.

## 2. Что входит и что не входит

**Входит:**

- **Удаление файлового хранилища целиком** (решение заказчика от 08.09.2026): остаётся только
  база, путь отката закрывается. Этим же закрывается шаг 33.58 фазы 33.
- Серверные сессии: таблица в базе, httpOnly-cookie, вход со сверкой argon2id, выход,
  «кто я», ротация и отзыв.
- Глобальный guard «закрыто по умолчанию» и декларативная пометка публичных маршрутов.
- Словарь прав «роль → что можно» одним объявлением.
- Перевод 36 маршрутов с личности из тела и query на сессию — тремя проходами, без разрыва фронта.
- Закрытие 28 открытых маршрутов и трёх режимов `?scope=all`.
- Проверка владельца при удалении клуба и тренера.
- Отзыв только при завершённой записи.
- Журнал аудита пишется только сервером.
- Серверная имперсонизация с двумя личностями в сессии.
- Серверные проверки страниц в трёх лейаутах и проброс сессии в слой доступа к данным.
- Ограничение частоты, `trust proxy`, заголовки безопасности, проверка `Origin`,
  тайм-аут геокодера, разделение ключей карт.
- Ограничитель числа одновременных проверок пароля.
- **Разделение прав представителя услуг и тренера** — решение заказчика от 08.09.2026:
  роли `club_owner` и `trainer` перестают быть одинаковыми по правам.
- **Восстановление пароля** — полный ход целиком, отправка письма за интерфейсом с токеном
  внедрения; сейчас заглушка, реальная служба подключается позже сменой реализации.
- Три вида проверки: обычные тесты, сторожа, чек-лист для браузера через Playwright MCP.

**Не входит:**

- Внешние провайдеры входа (Яндекс ID, VK ID, Google), магические ссылки.
- Второй фактор.
- Подключение реальной почтовой службы — провайдер выбирается позже, в фазе стоит заглушка
  за интерфейсом (образец — `FileStorage` / `FILE_STORAGE`).
- Движок политик (ABAC), таблица разрешений в базе, наследование ролей.
- Список активных устройств в интерфейсе (таблица сессий это позволит, экран — позже).
- Блокировка пользователя админом (`UserStatus` заложен и не используется) — отдельная работа.
- Redis, очереди, распределённое хранилище счётчиков частоты.

### 2.1 Решения заказчика (08.09.2026)

| Вопрос | Решение | Следствие |
| --- | --- | --- |
| Срок сессии пользователя | Перезаход раз в 14 суток | Предельный срок 14 суток; бездействие — столько же, отдельного порога нет |
| Срок сессии админа | Сутки без действий | Бездействие 24 часа, предельный 14 суток — забытая вкладка админа гаснет за сутки |
| Восстановление пароля | Закладываем **целиком**, службу подключим позже | Таблица одноразовых ссылок, маршруты, форма; отправка за интерфейсом с заглушкой |
| Блокировка после неудачных попыток | Блокируем: 5 попыток → 1 мин, следующие 5 → 2 мин, дальше +1 мин; верный вход обнуляет счётчик | Потолок 30 минут, чтобы не превращалось в вечный отказ |
| Отзыв после посещения | Меняем логику: отзыв только после завершённого занятия | На фронте вместо формы — плашка «сначала посетите занятие» |
| Разделение провайдера | Делаем **в этой фазе**: представитель услуг и тренер получают разные права | Отдельный этап Э8a: словарь прав, логика кабинета, тесты, чек-лист, прогон через Playwright MCP |
| Имя cookie | `__Host-sh-session` в бою, `sh-session` в разработке по http | одна константа |
| Файловое хранилище | **Удаляем целиком, первым этапом.** Остаётся только база | Новым таблицам не нужна вторая реализация; путь отката на файлы исчезает; 33.58 закрывается здесь |
| `POST /api/logs` | **Закрываем полностью:** запись с клиента убирается, журнал пишет только сервер | Чтение журнала — под правом администратора |
| Фикстуры и сид | Сводим в один набор, тренера заводим | `packages/fixtures` + `dev-seed.ts` |

⚠️ **Осознанный риск по удалению файлового хранилища.** Путь отката на боевом сервере исчезает:
если база не заведётся, вернуться будет некуда. Решение заказчика — удалять, проект всё равно
перезаливается заново. Перед удалением снимается архив `data/` и дамп базы (шаг 34.3a).

⚠️ **Осознанный риск по блокировке.** Блокировка по учётной записи означает, что зная чужую
почту, можно намеренно заблокировать вход её владельцу. Решение заказчика — блокировать.
Смягчение: счётчики ведутся раздельно по паре «почта» и по адресу обращения; верный пароль
сбрасывает оба, а потолок ожидания ограничен получасом.

## 3. Как устроен доступ

```
браузер ──cookie(httpOnly)──> Next (proxy.ts: редирект гостя)
                               │
                               ├─ RSC-страница ──> requireSession() ──> server-api.ts
                               │                                          │ пробрасывает cookie
                               └─ клиентский fetch ──/api/*── прокси ──────┤
                                                                          v
                                                  NestJS: SessionGuard (APP_GUARD)
                                                     │ нет сессии и нет @Public → 401
                                                     │ роль не подходит под @Requires → 403
                                                     v
                                                  контроллер: @CurrentUser()
                                                     v
                                                  сервис: AccessService — владение
                                                     v
                                                  репозиторий → база
```

Ключевое: **личность входит в систему ровно в одном месте** — в guard'е, из cookie. Ниже по
цепочке её никто не принимает параметром снаружи.

### 4.5 Что вскрылось по дороге

**Сторож утечки паролей станет ложно зелёным.** `password-leak.test.ts` обходит **все** маршруты
и ищет пароли в телах ответов. Как только маршруты закроются, он начнёт получать 401: тела
исчезнут, утечкам будет неоткуда взяться, тест позеленеет, ничего не проверяя. Плюс его
контрольная группа `USER_BEARING_ROUTES` (`:212-218`) требует `status < 300` и упадёт на четырёх
маршрутах из пяти. **Обвязка обязана научиться логиниться в том же шаге, где включается guard.**

**Эталон контрактов не содержит ни одного успешного входа.** Обе записи `POST /api/auth/login`
дают 404: снимок делался на почте `alexey@example.com`, а в фикстурах атлет заведён как
`alexey@sporthub.local`. Вход как таковой сверкой не покрыт вовсе.

**Фикстуры и dev-сид расходятся.** В фикстурах 3 пользователя (админ id=3, пароль
`admin-sporthub-2026`), в сиде 4 (админ id=1, пароль `sporthub123`), почты разные, а чек-листы
написаны по фикстурам. **Роли `trainer` в фикстурах нет вообще** — а «провайдер» на бэкенде это
`club_owner ∨ trainer`, то есть ветка входа тренера не покрыта ни одним тестом.

**В словаре текстов нет ни одного «нужен вход».** `error-messages.test.ts` закрепляет 38 текстов,
16 из них про вход и права, но текста для 401 без сессии брать неоткуда. Сам сторож ловит
исчезновение текста, но не ловит появление нового и не привязывает текст к маршруту.

**23 утверждения `toBe(401|403)` в 8 файлах меняют смысл** — сегодня они проверяют несовпадение
числа в теле, а не сессию.

## 5. Решения

### 5.1 Сессия в базе, а не токен

Сессию обязательно уметь **отзывать**: смена пароля, бан, выход со всех устройств, снятие
имперсонизации. Отзыв stateless-токена всё равно требует таблицы отозванных — то есть той же
таблицы, только второй сущностью и с обратной логикой. Для приложения с отрисовкой на сервере
и админкой сессия — общепринятый выбор.

В базе хранится **хеш** идентификатора (sha256), а не он сам: дамп базы не должен давать вход.
Тот же принцип, что уже применён к паролям в Ф33.

### 5.2 Почему не Better Auth и не Auth.js

Auth.js перешёл под команду Better Auth, новым проектам рекомендуют Better Auth. Нам он
не подходит по трём проверяемым причинам:

1. Он **владеет собственной схемой** — свои таблицы, camelCase, пароль в отдельной таблице.
   У нас 27 таблиц со snake_case-картами, миграциями и своим `users.password_hash`.
2. Его адаптер ходит в Prisma напрямую — это ломает границу, которую стережёт
   `database-boundary.test.ts:17,20`: клиент базы известен только `src/storage/`
   и `src/repositories/prisma/`.
3. Он приносит своих обработчиков и свою форму ответа, а у нас `{ success, data }` закреплена
   интерцептором и сверкой контрактов на 57 записей.

Нам нужен узкий набор: почта с паролем, cookie-сессия, роли, имперсонизация. Это 200–300 строк
своей реализации **по чужим правилам** (OWASP), а не свой протокол. Понадобятся внешние
провайдеры, магические ссылки или второй фактор — тогда Better Auth берётся целиком, а не
наполовину, и это отдельная фаза.

### 5.3 Форма сессии и cookie

Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, в бою с префиксом `__Host-`
(он требует `Secure` и `Path=/` и запрещает `Domain` — самая жёсткая привязка к хосту;
в локальной разработке по http префикс снимается). Значение — 256 бит случайности в base64url.
Прежняя `sh-auth-user-id` удаляется целиком, вместе с `auth-cookie.ts` и `auth-cookie-server.ts`.

Два срока жизни, как требует OWASP, — **оба**, а не один: по бездействию и предельный. Сроки
разные по роли и лежат одной константой в `packages/domain`. Новая роль получает политику
правкой одного словаря.

⚠️ **Скользящее продление пишется не чаще раза в 5 минут.** Наивная реализация обновляет
`last_seen_at` на каждом HTTP-запросе — и таблица сессий мгновенно становится самым горячим
писателем платформы. Это то же нарушение масштабируемости, которое пришлось чинить в 33.48,
и допускать его повторно нельзя.

### 5.4 Закрыто по умолчанию

Один глобальный guard через `APP_GUARD` — рядом с уже зарегистрированными `APP_INTERCEPTOR`
и `APP_FILTER` (`app.module.ts:62-63`). Маршрут без пометки требует сессии. Публичные помечаются
`@Public()`.

Смысл не в том, чтобы закрыть 28 дыр — их можно закрыть и руками. Смысл в том, что **маршрут,
который напишут через год, будет закрыт сам**. Это прямое требование расширяемости из «Главного
правила»: новое не должно создавать дыру самим фактом появления.

⚠️ Guard обязан бросать **наш** `UnauthorizedError`, а не исключение Nest. Ошибка из guard'а
минует интерцептор формата ответа (`api-response.interceptor.ts`), и только доменная ошибка
пройдёт через `DomainErrorFilter` и сохранит контракт `{ success: false, error }`.

### 5.5 Словарь прав, а не проверки россыпью

Список возможностей — в `packages/types/src/constants.ts` рядом с `USER_ROLES` и `LOG_ACTIONS`:
там живут все плоские словари проекта. Матрица «роль → набор прав» — в `packages/domain`
отдельным модулем по образцу `role-labels.ts` и `link-status.ts`, типом `Record<UserRole, …>`:
новая роль не соберётся, пока ей не выдали права.

Декоратор `@Requires('view_platform_logs')` на маршруте. Добавить возможность или переназначить
её роли = правка **одной** константы.

Это не абстракция впрок: потребителей уже трое (записи, админка, модерация), и есть назначенная
работа — разделение `provider` на тренера и владельца клуба вынесено в отдельную фазу; без
словаря оно станет правкой десятков мест. Движок политик и таблицу разрешений в базе не строим —
второго потребителя у них нет.

### 5.6 Владение остаётся в сервисах

`AccessService` уже есть и уже читает роль из базы: 17 точек вызова, `isAdmin`, `isManagerOfClub`,
`isManagerOfTrainer`, `isProviderOfBooking`. Меняется **только источник `userId`** — с тела
запроса на сессию. Проверку владения в декоратор не уносим: она требует загрузки сущности,
её место — сервис. Декоратор отвечает за «кто вообще может», сервис — за «эта ли его вещь».

### 5.7 Имперсонизация с двумя личностями

Сессия хранит настоящего пользователя (админа) и того, от чьего имени работаем.
**Права проверяются по второму, журнал пишется по первому.** Обе личности живут на сервере,
поэтому корректность записи в журнале не зависит от добросовестности клиента.

Начало и конец имперсонизации — серверные маршруты под правом `impersonate`. Под имперсонизацией
запрещены действия с учётными данными — проверяет это сервер, а не только скрытая форма.

### 5.8 Журнал только с сервера

Маршрута записи в журнал с клиента нет вовсе — `POST /api/logs` отвечает 404, у контроллера
остался только `@Get()` под правом администратора. События входа, выхода и имперсонизации пишет
сервер сам, исполнителя берёт из сессии. Новые действия журнала — правка `LOG_ACTIONS`
(26 значений), то есть одной константы.

### 5.9 Фронт: проверка у данных, а не у страницы

`server-api.ts` — уже слой доступа к данным с `server-only`, и документация Next называет
такой слой правильным местом для проверок. Туда садится проброс cookie и обработка 401 —
правка двух строк (`:75`, `:105`), а не тридцати страниц.

`proxy.ts` (в Next 16 `middleware` переименован в `proxy`, рантайм по умолчанию Node) — только
дешёвый редирект гостя по наличию cookie. Документация Next прямо предупреждает: proxy — не
защита, проверять надо у данных. Настоящее решение принимает бэкенд.

Серверный `requireSession(role?)` ставится в **три** лейаута: атлет, провайдер, админка.
RSC-поток перестаёт отдавать данные до проверки. 19 клиентских `AccessDeniedCard` остаются
как показ, но перестают быть защитой.

`useAuthStore` перестаёт быть источником истины: профиль и права приходят из `GET /api/auth/me`.
`MVP_*_USER_ID` удаляются — в прод-коде используется только `MVP_ADMIN_USER_ID`, в одном месте.

### 5.10 CSRF

`SameSite=Lax` закрывает основной сценарий, но одного его мало. Добавляем проверку
`Sec-Fetch-Site` / `Origin` на изменяющих методах — одна middleware, без токенов и без правки
форм. Токены не заводим: они требуют состояния и трогают каждую форму, а выигрыш при
первопартийной cookie, одном хосте и отсутствии поддоменов близок к нулю.

Отдельно проверяем сторожем, что изменяющих `GET`-маршрутов нет: `SameSite=Lax` их пропускает.

### 5.11 Частота и защита argon2 от исчерпания памяти

Берём `@nestjs/throttler` — своё не пишем, у него уже подменяемое хранилище (память сейчас,
Redis потом без правки бизнес-кода). Ограничения: вход по паре «адрес + почта» (иначе
распределённый перебор одного аккаунта проходит мимо ограничения по адресу), регистрация
по адресу, гео-прокси по адресу.

⚠️ **`trust proxy` обязателен.** Без него за nginx все запросы приходят с одного адреса,
и ограничение либо не работает, либо блокирует всех разом.

⚠️ **argon2id — вектор исчерпания памяти, а не только цена входа.** Параметры Ф33: 19 МБ,
две итерации, одна дорожка. 19 МБ выделяется на **каждую параллельную** проверку; сотня
одновременных входов — почти два гигабайта, а машина ровно такого порядка. Нужен ограничитель
числа одновременных проверок пароля (очередь), а не ослабление параметров хеша.

### 5.12 Утечки через ответы входа

Единое сообщение «Неверная почта или пароль» вместо трёх разных, и сверка пароля выполняется
даже для несуществующей почты (по фиктивному хешу) — иначе по времени ответа перечисляют
заведённые аккаунты. Регистрация перестаёт подтверждать занятость почты прямым текстом.

Проверка «тип кабинета не совпал» остаётся, но переезжает **после** сверки пароля и становится
удобством интерфейса, а не защитой.

### 5.13 Данные в ответах

⚠️ **`GET /api/users` нельзя просто закрыть.** На нём висят публичные страницы клуба, тренера
и записи (`clubs/[slug]/page.tsx:70`, `trainers/[slug]/page.tsx:55`, `booking/[scheduleId]/page.tsx:56`) —
они тянут всех пользователей, чтобы подписать автора отзыва: в типе `Review`
(`packages/types/src/types.ts:327-333`) имени нет.

Порядок: сначала необязательное поле `authorName` в ответе отзывов (старый клиент переживает),
затем публичные страницы переводятся на него, и только потом `GET /api/users` уходит под право
`manage_any_user`. Провайдеру — узкий маршрут своих клиентов вместо полного списка.

## 6. Схема: таблица `sessions`

### 6.1 Модель

Соглашения `schema.prisma` соблюдаются дословно: camelCase-поле + `@map("snake_case")`,
`@@map` последней строкой, явные `@db.VarChar(n)`, комментарий `///` на каждый индекс.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | `Int @id @default(autoincrement())` | номер, как во всех 27 таблицах |
| `tokenHash` | `String @unique @db.VarChar(64)` | sha256 идентификатора в hex |
| `userId` | `Int` | владелец сессии, `onDelete: Cascade` |
| `impersonatedUserId` | `Int?` | заполнено только под имперсонизацией, `onDelete: SetNull` |
| `createdAt` | `DateTime @default(now())` | выдача |
| `lastSeenAt` | `DateTime` | продление, пишется не чаще раза в 5 минут |
| `expiresAt` | `DateTime` | предельный срок |
| `revokedAt` | `DateTime?` | отзыв: выход, смена пароля, бан |
| `userAgent` | `String? @db.VarChar(512)` | разбор инцидентов, будущий список устройств |
| `ip` | `String? @db.VarChar(64)` | то же |

Роль в сессии **не хранится** — она читается из пользователя. Иначе словарь ролей окажется
в двух местах, и смена роли не подействует до перелогина.

### 6.2 Индексы

| Индекс | Под какой запрос |
| --- | --- |
| `@@unique([tokenHash])` | проверка сессии на каждом запросе — единственный горячий путь |
| `@@index([userId])` | отзыв всех сессий пользователя одним `UPDATE` |
| `@@index([expiresAt])` | уборка протухших |

Мёртвых индексов не заводим: у каждого перечисленного есть названный потребитель.
После фазы `idx_scan` по `sessions` обязан расти — это проверяется так же, как в Ф33.

### 6.3 Ограничения

В `scripts/db-constraints.mjs` — там, где живут все ограничения, не выразимые Prisma:

- `sessions_expires_after_created` — `expires_at > created_at`;
- частичный индекс `sessions_active_idx` по `user_id` с предикатом «не отозвана» —
  предикат берётся из набора в `packages/domain`, а не пишется литералом.

Сверку объявленного с фактическим делает существующий `schema.test.ts` — он импортирует
сам скрипт и сравнивает с базой.

### 6.4 Уборка

Протухшие сессии удаляет отдельная команда (`npm run db:sessions:prune`), а не запрос
пользователя: чистка внутри горячего пути — это скрытая работа на чужом запросе.

## 7. Ловушки — где поведение поедет молча

### 7.1 Сторож утечки паролей позеленеет впустую

Разобрано в 4.5. Лечится в том же шаге, где вводится guard: обвязка получает `harness.as(user)`,
`USER_BEARING_ROUTES` вызываются с сессией, и добавляется отдельное утверждение — «контрольная
группа отвечает успехом **под сессией** и 401 **без неё**».

### 7.2 Guard бросит не ту ошибку и сломает форму ответа

`UnauthorizedException` из Nest пройдёт мимо интерцептора и даст форму без нашей обёртки.
Разобрано в 5.4. Диверсия d-8 это проверяет.

### 7.3 Cookie не долетит до бэкенда при отрисовке на сервере

Браузерные запросы идут через проксирование Next и несут cookie сами. Запросы страниц идут
из `server-api.ts` **напрямую** на `SPORT_HUB_API_ORIGIN` и заголовков не передают вовсе.
Забыть про это — значит получить «в браузере работает, на странице пусто».

### 7.4 Ротация сессии на входе

Без выдачи нового идентификатора при входе остаётся фиксация сессии: подсунул жертве свой
идентификатор до входа — после входа он становится валидным для её учётной записи.

### 7.5 Смена пароля не гасит остальные сессии

Смена пароля гасит все сессии пользователя, кроме текущей.

### 7.6 `?scope=all` останется чёрным ходом

Три маршрута меняют смысл по параметру. Закрыть маршрут, не закрыв режим, — значит оставить
дыру под правильной вывеской. Каждый режим либо убирается, либо требует права.

### 7.7 Публичные страницы упадут вместе с `/api/users`

Разобрано в 5.13. Порядок шагов в Э4 обязателен: сначала `authorName`, потом закрытие.

### 7.8 Тесты сервисов переживут фазу, а тесты маршрутов — нет

27 тестовых файлов бэкенда HTTP не дёргают и от закрытия маршрутов не пострадают. Но три из них
(`booking.service.test.ts`, `concurrency.test.ts`, `publication.service.test.ts`) оперируют
`userId` на уровне сервисов — они сломаются, если поменяется **сигнатура сервисов**. Поэтому
сигнатуры сервисов не трогаем: личность как была аргументом сервиса, так и остаётся, меняется
только то, кто её туда кладёт.

## 8. Что нельзя сломать

### 8.1 Формы ответа

`{ success: true, data }` и `{ success: false, error }` остаются. 401 и 403 отдаются в той же
форме, что и прочие доменные ошибки. Три сохранённых отклонения Ф32 (ответ без `data`, счётчики
рядом с `data`, счётчики внутри `data`) не трогаются.

### 8.2 Тексты ошибок

38 закреплённых текстов остаются в коде дословно, кроме трёх текстов входа, которые заменяются
одним (см. 5.12). Замена оформляется правкой `REQUIRED_MESSAGES` в том же шаге — иначе сторож
покраснеет и остановит работу. Новые тексты («Требуется вход», «Недостаточно прав») добавляются
в список: сторож ловит исчезновение, но не появление, поэтому пополнять его надо руками.

### 8.3 Публичная часть остаётся публичной

Каталог, карточки клуба и тренера, расписание, чтение отзывов, справочники, вход и регистрация —
доступны без сессии. По эталону контрактов это 19 записей из 57. Гость обязан видеть сайт.

### 8.4 Записи, расписание, FSM

Правила переходов, атомарность счётчика мест, автопереходы по времени — не трогаются вовсе.
Фаза меняет ответ на вопрос «кто это делает», а не «что происходит».

## 9. Главное правило — проверяемый чек-лист фазы

| Принцип | Что проверяем | Как убеждаемся |
| --- | --- | --- |
| **Масштабируемость** | Сессия ищется одним запросом по уникальному индексу; `last_seen_at` пишется не чаще раза в 5 минут; отзыв всех сессий — один `UPDATE` по индексу; ограничение частоты не хранит строку на запрос; проверка пароля ограничена по параллелизму | `idx_scan` по `sessions` растёт; нагрузочный прогон входа; тест продления |
| **Расширяемость** | Новая роль = правка `ROLE_CAPABILITIES`; новый маршрут закрыт сам; новый публичный — один декоратор; новое поле ответа (`authorName`) необязательное | Тип `Record<UserRole, …>` не соберётся без прав; сторож маршрутов |
| **Улучшаемость** | Один словарь прав, один `AccessService`, один `requireSession`, одна точка проброса cookie; неподключённые `ZodValidationPipe` / `EntityIdPipe` удалены | Поиск дублей; ревью по завершении Э8 |
| **Модернизируемость** | Сессии за репозиторием с токеном внедрения; хранилище частоты подменяемое; guard не знает про Prisma | `database-boundary.test.ts` и `storage-boundary.test.ts` остаются зелёными |
| **База** | `sessions` с каскадом, уникальность в базе, ограничения в общем скрипте, комментарий на каждый индекс | `schema.test.ts` |
| **Без абстракций впрок** | Нет движка политик, таблицы разрешений, наследования ролей, внешних провайдеров | Раздел 2 «не входит» |

⚠️ Список известных расхождений в `STACK_OVERVIEW.md` эта фаза обязана **сократить**, а не
пополнить: из него уходят семь строк — про пароль на входе, личность из тела, удаление
публикаций, подделку журнала, серверные guard'ы, `error.tsx` и отсутствие ограничения частоты.

## 10. Порядок работ — десять этапов

| Э | Название | Почему именно здесь |
| --- | --- | --- |
| Э0 | Задание и тест-кейсы | Чек-листы пишутся до кода — как в Ф33 |
| Э0a | Удаление файлового хранилища | До сессий: иначе новым таблицам пришлось бы писать вторую реализацию в мусор |
| Э1 | Сессии | Всё остальное опирается на них |
| Э2 | Каркас доступа | Guard и обвязка тестов вводятся **одним** этапом, иначе сторож паролей зеленеет впустую |
| Э3 | Личность из сессии | 36 маршрутов, тремя проходами |
| Э4 | Дыры чтения | После Э3: закрывать нечем, пока нет сессии |
| Э5 | Владение и правила | Меняет продуктовое поведение — отдельно и заметно |
| Э6 | Админка и имперсонизация | Опирается на права из Э2 |

### 12.2 Новые тесты

**Сессии:** выдача даёт разные значения; в базе лежит хеш, а не сам идентификатор; продление
не чаще раза в 5 минут; истечение по бездействию; истечение по предельному сроку; ротация при
входе; отзыв при выходе; отзыв всех при смене пароля; каскад при удалении пользователя.

**Guard и права:** непубличный маршрут без сессии — 401; публичный без сессии — 200; роль без
права — 403; право есть, но чужая вещь — 403; свой — 200; форма ответа 401 совпадает с общей.

**Вход:** верный пароль — 200 и `Set-Cookie` с `HttpOnly`; неверный пароль и несуществующая почта
дают одинаковый текст и одинаковый код; ограничитель параллельных проверок держит очередь;
превышение частоты — 429.

**Дыры:** чужой ЛК, чужие заметки, чужое удаление публикации, подделка журнала, отзыв без
посещения, `?scope=all` без права, `/api/users` гостю, `/api/logs` гостю.

**Имперсонизация:** права по цели, журнал по админу; не-админ не может; смена учётных данных
под имперсонизацией запрещена.

## 16. Что нашёл браузерный прогон (34.68, 09.09.2026)

Пять дефектов. Ни один не был виден ни одному из 2042 тестов, и все пять — одного
класса: **проверялась логика, а не то, что ею пользуются**. Серверная часть была
написана, покрыта тестами и работала; не работало соединение её с браузером.

| # | Что | Почему тесты молчали |
| --- | --- | --- |
| 1 | Карта на главной не грузилась вовсе: правила источников (CSP) разрешали адрес API карт, но загрузчик третьей версии тянет пакет и стили с отдельного узла раздачи | Заголовок проверялся на наличие директив, а не на то, доедет ли по ним карта. Ошибка видна только в консоли браузера |
| 2 | Имперсонизация **никогда не звала сервер**: браузер правил только свой стор. Плашка исчезала после перезагрузки, а подменённый кабинет не открывался вовсе — серверная проверка роли видела администратора | Серверные маршруты покрыты, вызовов из браузера не было ни одного. Тесты страниц мокали слой данных |
| 3 | Роль исполнителя в журнале записана литералом: 16 мест из 22, плюс 4 места брали личность у подменённой, а не у настоящей | Тесты сверяли, что запись появилась, а не что в ней написано |
| 4 | Чужой `Origin` принимался: список разрешённых источников пуст по умолчанию, а пустой означал «пропускать любой». Запрос с чужого сайта без `Sec-Fetch-Site` создавал запись | Тест проверял путь по `Sec-Fetch-Site`; путь по `Origin` был выключен настройкой, которую никто не заполнял |
| 5 | Повторный отзыв проходил: один человек с одним посещением сдвинул рейтинг клуба с 5 на 4.7 | Правило «одна оценка на посещение» было записано в чек-листе и не написано в коде |

Отдельно, не дефект фазы, но дыра в продукте: **роль `trainer` недостижима**.
Регистрация назначает представителю услуг `club_owner` жёстко
(`auth.controller.ts`), смены роли администратором в проекте нет. Словарь прав
тренера и владельца клуба разводит, но получить тренера можно только сидом.
Решать заказчику: третий тип учётной записи при регистрации или назначение роли
из админки.

Ещё сверка чек-листа с кодом нашла **семь устаревших шагов** — они требовали одного,
а код сознательно делает другое (открытый геокодер, удалённый маршрут журнала,
форма отзыва вместо плашки и т.д.). Текст чек-листа выправлен; таблица — в отчёте.
