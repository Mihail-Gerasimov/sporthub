## Phase 14: Dynamic Provider Publish Flow — очистка старой витрины и переход к живому каталогу

> После этой фазы: старая статичная витрина клубов и тренеров больше не используется как источник публичной части. Новые клубы и тренеры создаются только из `/profile/provider` через две publish-модалки, записываются в JSON через `API -> db.ts`, появляются в ЛК, участвуют в каталогах, detail pages и booking-flow.

Phase 14 переводит проект от старой seed-витрины к динамическому каталогу, который формируется из ЛК представителя спортивных услуг.
Работаем только с двумя существующими пользователями:
- `userId=1` — athlete;
- `userId=2` — provider.

Новые пользователи и новые регистрации пока не учитываются.
Реальной в этой фазе становится именно динамика публикаций и их прохождение по проекту.
Fake/stub-функции, которые уже честно помечены как `будет позже`, сохраняются и не блокируют create-flow.

**Ключевые решения:**

- Старые seed-карточки `clubs` и `trainers` очищаются и больше не считаются рабочим каталогом.
- Справочные seed-данные сохраняются только там, где они реально нужны:
  - `sports.json`;
  - `users.json`.
- Все новые публикации создаются от имени существующего provider-пользователя `id=2`.
- Для новых клубов и тренеров используется единая служебная модель:
  - `source: 'provider' | 'seed'`;
  - `managedByUserId`;
  - `status`;
  - `slug`.
- Для новых публикаций по умолчанию:
  - `source = 'provider'`;
  - `managedByUserId = 2`;
  - `status = 'published'`.
- Реальная загрузка фото, галерея и похожие future-функции не входят в scope этой фазы.
- Фото и медиа для новых публикаций остаются на placeholder/stub-уровне, чтобы текущий UI продолжал работать без file upload.
- Новая публикация должна быть сразу пригодна для текущего UI:
  - клуб создаётся как `club + offering + schedule[]`;
  - тренер создаётся как `trainer + offering + schedule[]`.
- KPI в ЛК переводятся на реальную динамику там, где есть настоящий источник данных; остальные блоки получают честный `0` или маркируются как demo/MVP.
- После очистки старой витрины проект обязан корректно жить в пустом состоянии до первой публикации.

### Step 14.5: Реализовать atomic JSON write-flow через API и db.ts

- **Действие:**
  - добавить отдельные POST endpoints:
    - для создания клуба;
    - для создания тренера;
  - на сервере валидировать payload через `Zod`;
  - в `db.ts` реализовать create-функции, которые пишут связанные коллекции единым сценарием;
  - pseudo-atomic write для JSON (MVP): собрать все данные в памяти, провалидировать, и только потом записать все файлы последовательно. Не настоящий atomic, но достаточно для MVP с одним пользователем;
  - не допускать partial write:
    - либо создаётся весь набор сущностей;
    - либо не создаётся ничего;
  - стратегия генерации ID: `max(existing_ids) + 1`, при пустой коллекции стартовый ID = 1;
  - на create сразу выставлять:
    - `id`;
    - `slug`;
    - `createdAt`;
    - `source`;
    - `status`;
    - `managedByUserId`;
    - safe defaults для UI.

**Проверка:**

- создание идёт только по цепочке `modal -> API -> db.ts -> JSON`;
- валидный payload создаёт корректный набор связанных данных;
- невалидный payload не оставляет мусорных записей.

**Тесты:**

- API success/failure tests для клуба и тренера;
- db-level tests на atomic create;
- tests на отсутствие partial writes при ошибке.

**Ожидаемый результат:**

- данные создаются по архитектурным правилам проекта и не ломают JSON-модель.
