## Phase 15: Provider Publication Edit Flow

> После этой фазы: авторизованный fake-provider может открыть любую публикацию из блока `Мои публикации`, отредактировать активные MVP-поля клуба или тренера в предзаполненной модалке и сохранить изменения в JSON через `PATCH -> API -> db.ts`, без создания дубликатов сущностей и без изменения существующего визуального стиля кабинета.

Phase 15 расширяет уже существующий publish-flow.
В проекте уже есть рабочие publish-модалки, create-flow через `API -> db.ts -> JSON` и живой блок `Мои публикации`, поэтому редактирование строится как продолжение этой архитектуры, а не как отдельная пара новых UI-форм. 

**Ключевые решения:**

- Использовать существующие `PublishClubModal` и `PublishTrainerModal`, добавив режим `mode: 'create' | 'edit'`.
- Не делать отдельные edit-модалки с дублированием разметки.
- Edit-flow вызывается только из `/profile/provider` → блок `Мои публикации`.
- Рядом с действием удаления добавить action `Редактировать`.
- В режиме `edit` модалка получает `entityId` и `initialData`, а поля открываются предзаполненными.
- Редактирование доступно для всех публикаций, которые видны текущему fake-provider в `Мои публикации`, то есть для сущностей с `managedByUserId = userId`.
- Сохранение идёт через `PATCH -> API -> db.ts -> JSON`.
- Update-flow обязан изменять существующую публикацию, а не создавать новый клуб/тренера или основную услугу поверх старых данных.
- В рамках текущего MVP клуб и тренер по-прежнему имеют одну основную услугу (`primary offering`), которую и нужно редактировать.
- Редактирование включает и расписание: существующие слоты обновляются с сохранением `id`, новые слоты создаются, удалённые слоты убираются из JSON.
- Future/stub-поля остаются вне scope редактирования.
- `slug`, `createdAt`, `source`, `status`, рейтинг, `reviewCount`, `imageUrls` и прочие неактивные поля не редактируются и сохраняются как есть.
- После сохранения изменения сразу отражаются в `Мои публикации`, KPI, каталогах и detail pages. 

### Step 15.1: Зафиксировать scope редактирования и update-contract

- **Действие:**
  - зафиксировать, что редактируются только активные MVP-поля из существующих publish-модалок;
  - вынести общий `form-state` (`ScheduleSlotForm`, `ClubFormState`, `TrainerFormState`) в `src/lib/schemas/publish.ts` — рядом с Zod-схемами, без создания отдельного файла;
  - расширить `ScheduleSlotForm` полем `id?: number` для поддержки edit существующих слотов;
  - исключить из scope future/stub-поля;
  - определить update-payload для клуба и тренера: используется та же Zod-схема что и для create (full replace, не partial patch — все поля обязательны);
  - зафиксировать, что `PATCH` получает `userId` в body, а ownership проверяется по `managedByUserId === userId`;
  - зафиксировать, что редактирование доступно для любых публикаций, отображаемых в `Мои публикации` текущего fake-provider;
  - зафиксировать, что `slug` и прочие неактивные системные поля в рамках Phase 15 не редактируются.

- **Проверка:**
  - update-contract не выходит за пределы текущего MVP;
  - create-flow и edit-flow не конфликтуют между собой;
  - contract явно описывает, какие поля редактируются, а какие сохраняются без изменений.

- **Тесты:**
  - contract-level тесты на shared form-state и edit payload;
  - тесты на игнорирование future/stub-полей.

- **Ожидаемый результат:**
  - появляется чёткий и ограниченный контракт редактирования без скрытых решений на этапе реализации.

### Step 15.2: Подготовить reverse-mapping для предзаполнения edit-форм

- **Действие:**
  - добавить mapping из persisted сущностей обратно в form-state:
    - `club + primary offering + schedule[] -> ClubFormState`
    - `trainer + primary offering + schedule[] -> TrainerFormState`
  - переносить `id` существующих schedule slots в form-state;
  - восстанавливать значения `disciplines`, `sport`, `specializations`, `clubId` и остальных активных полей из текущих persisted данных;
  - использовать этот mapping для `initialData` в edit-модалках.

- **Проверка:**
  - модалка редактирования открывается уже с заполненными полями;
  - disciplines, specializations и schedule-слоты не теряются;
  - существующие slot `id` не теряются между загрузкой edit-form и submit.

- **Тесты:**
  - unit-тесты на reverse-mapping клуба;
  - unit-тесты на reverse-mapping тренера;
  - тесты на roundtrip `persisted -> form-state -> payload` для существующих schedule slots.

- **Ожидаемый результат:**
  - edit-формы получают стабильный и переиспользуемый источник initial state.

### Step 15.3: Реализовать atomic update-flow в `db.ts`

- **Действие:**
  - добавить update-функции для клуба и тренера;
  - обновлять агрегат целиком:
    - owner entity;
    - связанную основную услугу;
    - связанные schedule slots;
  - сохранить pseudo-atomic pattern: сначала сборка и валидация в памяти, потом запись JSON;
  - не допускать partial update;
  - не допускать update чужих или несуществующих provider-публикаций;
  - не создавать второй `offering` поверх уже существующего `primary offering`;
  - обновлять существующие schedule slots по `id` с сохранением `createdAt` и `bookedCount`;
  - создавать новые slots только для элементов без `id`;
  - удалять из JSON только те slots, которые были связаны с публикацией и не пришли в новом payload.

- **Проверка:**
  - редактирование изменяет существующую публикацию, а не создаёт дубликат;
  - offering и schedule не дублируются;
  - update существующего slot сохраняет его идентичность через тот же `id`.

- **Тесты:**
  - db-level success/failure tests;
  - tests на ownership guard;
  - tests на отсутствие partial writes;
  - tests на diff расписания: update existing slot, add new slot, remove deleted slot;
  - test на стабильность `slug` при изменении `name`/`firstName`/`lastName` — slug не меняется после update.

- **Ожидаемый результат:**
  - data-layer безопасно поддерживает update существующих публикаций.

### Step 15.4: Добавить PATCH API для клуба и тренера

- **Действие:**
  - реализовать:
    - `PATCH /api/clubs/[id]`
    - `PATCH /api/trainers/[id]`
  - валидировать payload через `Zod` на основе текущих publish-схем;
  - использовать `id` публикации из route param, а ownership проверять по `userId` из body;
  - вызывать update-функции из `db.ts`;
  - вернуть стандартный контракт ответа проекта;
  - подготовить bootstrap-данные для открытия edit-модалки:
    - расширить `GET /api/clubs/[id]` primary offering для edit-flow;
    - использовать `GET /api/trainers/[id]` как источник trainer edit-context.

- **Проверка:**
  - валидный PATCH обновляет публикацию;
  - невалидный PATCH не оставляет мусорных изменений;
  - API умеет вернуть все данные, необходимые для предзаполнения edit-формы.

- **Тесты:**
  - API success/failure tests;
  - тесты на validation error / not found / forbidden;
  - тесты на bootstrap edit-context для клуба и тренера.

- **Ожидаемый результат:**
  - edit-flow идёт по той же архитектурной цепочке, что и create-flow.

### Step 15.5: Перевести publish-модалки в режим `create/edit`

- **Действие:**
  - добавить в `PublishClubModal` и `PublishTrainerModal` поддержку `mode`;
  - в режиме `edit`:
    - поменять title и primary button label;
    - заполнять форму через `initialData`;
    - отправлять submit в PATCH endpoint;
    - передавать `entityId` и `userId`;
  - сохранить существующую client-side валидацию и применить её к edit-flow;
  - расширить существующие `buildClubPayload` / `buildTrainerPayload` параметром `entityId` вместо создания отдельных edit-функций; в create `entityId` не передаётся, в edit — передаётся;
  - не делать второй параллельный state и вторую реализацию разметки для edit-режима.

- **Проверка:**
  - одна и та же форма работает и на create, и на edit;
  - edit submit не вызывает create endpoint;
  - close/reopen корректно сбрасывает create-state и корректно переинициализирует edit-state.

- **Тесты:**
  - modal tests для `create`/`edit` режимов;
  - edit submit success/error;
  - reset/close/reopen tests;
  - тесты на передачу slot `id` в edit submit.

- **Ожидаемый результат:**
  - UI редактирования собран без второй параллельной реализации форм.

### Step 15.6: Подключить action `Редактировать` в блоке `Мои публикации`

- **Действие:**
  - рядом с `Удалить` добавить `Редактировать`;
  - по клику:
    - клуб открывает `PublishClubModal` в режиме `edit`;
    - тренер открывает `PublishTrainerModal` в режиме `edit`;
  - перед открытием модалки загружать актуальный edit-context по `entityId`;
  - передавать в модалку корректные `entityId` и `initialData`;
  - сохранить текущий внешний вид секции `Мои публикации` без редизайна карточек.

- **Проверка:**
  - редактирование запускается прямо из provider cabinet;
  - delete-flow не ломается;
  - edit action работает и для уже существующих карточек из текущих JSON, и для новых публикаций.

- **Тесты:**
  - тесты на рендер кнопки `Редактировать`;
  - тесты на открытие корректной модалки;
  - regression на delete action;
  - тесты на загрузку edit bootstrap перед открытием модалки.

- **Ожидаемый результат:**
  - у провайдера появляется реальная точка входа в edit-flow.
