# Выкатка на боевой сервер

Порядок действий для шагов 33.49–33.59 фазы 33. Пишется заранее, чтобы выкатка была
последовательностью проверяемых шагов, а не импровизацией в окне простоя.

Сервер: reg.cloud VPS, Ubuntu 24.04, панель FastPanel, домен `athletehub.ru`,
webroot `/var/www/fastuser/data/www/athletehub.ru/`.

---

## 0. Перед началом — копия боевых данных (33.49)

⚠️ Бэкапы базы решением заказчика не делаются, проект в стадии пробной версии. Значит
копия перед переносом — **единственная** страховка, и она снимается вручную.

```bash
ssh root@<адрес>
cd /var/www/fastuser/data/www/athletehub.ru
tar czf ~/sporthub-data-$(date +%F).tar.gz data/
```

Скачать архив к себе. Пока он не у вас на машине — дальше не идти.

**Аудит боевого набора.** Весь аудит §4.7 файла фазы сделан по локальному `data/`. На боевом
лежат живые публикации и записи клиентов, и набор битых строк там другой. Прогнать тот же
разбор по скачанному архиву и решить по каждому найденному случаю ДО переноса.

## 1. Машина и контейнеры (33.50)

```bash
# Docker и compose
curl -fsSL https://get.docker.com | sh
docker --version && docker compose version

# Пользователь без прав суперпользователя для запуска
usermod -aG docker fastuser
```

Проверить свободное место: образы бэкенда и фронта вместе занимают около 1.7 ГБ,
база с данными — десятки мегабайт, журналы растут.

## 2. База и учётная запись (33.51)

Пароль задаётся переменной `POSTGRES_PASSWORD` в `.env` рядом с `docker-compose.yml`.
Значение по умолчанию из репозитория на боевом сервере **не годится**.

```bash
cd /var/www/fastuser/data/www/athletehub.ru
printf 'POSTGRES_PASSWORD=%s\n' "$(openssl rand -base64 24)" > .env
chmod 600 .env
docker compose up -d db
docker compose logs db | tail -20
```

⚠️ Порт базы публикуется только на `127.0.0.1` — наружу она не смотрит. Проверить:

```bash
ss -tlnp | grep 5434     # должен быть только 127.0.0.1
```

## 3. Секреты (33.52)

| Переменная | Где задаётся | Замечание |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | `.env` рядом с compose | см. выше |
| `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` | аргумент сборки образа фронта **и** окружение бэкенда | во фронте вшивается в бандл на сборке |
| `YANDEX_SUGGEST_API_KEY` | окружение бэкенда | серверный, наружу не уходит |

⚠️ Файлы окружения в образ не копируются намеренно: слой образа неизменяем, вычистить
из него ключ потом нельзя — только пересобрать образ и отозвать ключ.

## 4. Миграция и перенос данных (33.53)

Порядок обязателен: **сначала схема, потом код**. Аддитивная миграция безопасна для ещё
работающего старого кода; обратный порядок даёт окно, в котором новый код обращается
к колонкам, которых ещё нет.

```bash
docker compose --profile migrate run --rm migrate
docker compose run --rm api node dist/storage/seed/import-from-files.js
```

Скрипт переноса печатает отчёт: сколько строк по каждой таблице, что починено, что
пересчитано. Отчёт сохранить — он часть приёмки.

**Окно простоя допустимо** (решение заказчика). На время переноса приложение остановить,
чтобы никто не создал запись, которая не попадёт в базу.

## 5. Проксирование, домен, сертификат (33.54)

nginx не трогаем. Он проксирует на `127.0.0.1:3000`, и контейнер фронта публикует ровно этот
адрес и порт. Для nginx смена способа запуска незаметна. Сертификат Let's Encrypt
продлевается сам, как и раньше.

## 6. Переключение и вывод pm2 (33.55)

```bash
pm2 delete all
pm2 unstartup          # ⚠️ без этого автозапуск вернётся после перезагрузки
docker compose --profile app up -d
docker compose --profile app ps
curl -s http://127.0.0.1:3001/api/health
```

⚠️ Если пропустить `pm2 unstartup`, после первой же перезагрузки pm2 поднимет свои два
процесса на портах 3000 и 3001 — тех же, что публикуют контейнеры. Половина запросов уйдёт
в старый процесс, половина в новый, и диагностируется это часами.

## 7. Откат (33.56)

```bash
docker compose --profile app down
pm2 start ecosystem.config.cjs
```

Файловая реализация хранилища и `data/*.json` живы до конца фазы именно ради этого шага.

⚠️ Откат возвращает и почищенные тексты. Мусорные значения (нецензурные причины отмены,
названия залов, имя тестового пользователя) правятся при переносе В БАЗУ; в файлах они
остались как были. Возврат на файлы вернёт их вместе с данными.

⚠️ Окно отката ограничено. Записи, сделанные уже через базу, в файлах отсутствуют: чем
дольше работает база, тем больше данных потеряет возврат на файлы. Решение об откате
принимается в первые часы, а не через неделю.

## 8. Проверка на боевом (33.57)

Полный прогон `tests/checklists/phase-33-database.md` — те же 73 шага, отдельный отчёт
в `tests/reports/`. Только после зелёного прогона можно переходить к удалению файловой
реализации.

⚠️ Нагрузочный замер на боевом **не гоняется никогда**: он создаёт настоящие записи
и меняет статусы.

## 9. Удаление файлового пути (33.58)

Только после копии из шага 0, после зелёного прогона на боевом и после пунктов 1–8 приёмки.

## 10. Эксплуатация (33.59)

| Что | Как |
| --- | --- |
| Журналы | `docker compose --profile app logs -f <сервис>` |
| Ротация журналов | драйвер `json-file` с ограничением размера в настройках демона |
| Расход памяти | `docker stats` — заменяет прежний `pm2 status` |
| Место под базу | `docker system df -v` и размер тома `sporthub_pgdata` |
| Состояние процессов | `docker compose --profile app ps` |

Автозапуск обеспечивает сам Docker: у всех сервисов `restart: unless-stopped`.
