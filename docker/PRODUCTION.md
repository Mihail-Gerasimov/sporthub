# Выкатка на боевой сервер

Порядок действий при выкатке: последовательность проверяемых шагов, а не импровизация
в окне простоя.

Сервер: reg.cloud VPS, Ubuntu 24.04, панель FastPanel, домен `athletehub.ru`,
webroot `/var/www/fastuser/data/www/athletehub.ru/`.

---

## 0. Перед началом — копия боевых данных

⚠️ Бэкапы базы решением заказчика не делаются, проект в стадии пробной версии. Значит
копия перед рискованной операцией — **единственная** страховка, и она снимается вручную.

Копия снимается **дампом базы**: другого хранилища у приложения нет.

```bash
ssh root@<адрес>
cd /var/www/fastuser/data/www/athletehub.ru
docker compose exec -T db pg_dump -U sporthub -d sporthub | gzip > ~/sporthub-db-$(date +%F).sql.gz
```

Скачать архив к себе. Пока он не у вас на машине — дальше не идти.

⚠️ На **самой первой** выкатке снимать нечего: базы на сервере ещё нет. Тогда шаг
пропускается, а данные берутся по §5.3. Начиная со второй выкатки шаг обязателен —
восстановление дампа теперь единственный откат (§8).

**Аудит боевого набора.** Разбор битых строк из §4.7 файла фазы делался по локальному
набору. На боевом лежат живые публикации и записи клиентов, и набор битых строк там
другой. Прогнать тот же разбор по боевой базе (запросы §5.1) и решить по каждому
найденному случаю ДО наката миграций.

## 1. Машина и контейнеры

```bash
# Docker и compose
curl -fsSL https://get.docker.com | sh
docker --version && docker compose version

# Автозапуск демона после перезагрузки: без него `restart: unless-stopped`
# у сервисов ничего не значит — поднимать контейнеры будет некому.
systemctl enable --now docker

# Пользователь без прав суперпользователя для запуска
usermod -aG docker fastuser
```

Свободное место: два рабочих образа занимают **186 МБ** (бэкенд) и **386 МБ** (фронт),
вместе около 572 МБ; образ базы — ещё около 165 МБ. Плюс сама база с данными (десятки
мегабайт) и растущие журналы. Считать от 2 ГБ свободного места, не меньше.

### 1.1 Перенос образов на сервер

⚠️ Собирать образы **на боевом сервере нельзя**: сборка — это `npm ci` всего
монорепозитория и `tsc`, на машине с двумя гигабайтами это в лучшем случае долго.
Образы собираются на машине разработки под платформу сервера и переносятся готовыми.

На машине разработки:

```bash
npm run images:build:server        # buildx, linux/amd64 → sporthub-api:latest, sporthub-web:latest
docker save sporthub-api:latest sporthub-web:latest | gzip > sporthub-images.tgz
scp sporthub-images.tgz root@<адрес>:/tmp/
```

На сервере:

```bash
gunzip -c /tmp/sporthub-images.tgz | docker load
docker images | grep sporthub          # обе метки на месте
```

⚠️ Сами по себе эти метки compose не подхватит: у сервисов `api` и `web` описана сборка,
и имя образа compose выводит из имени проекта — в каталоге `athletehub.ru` это было бы
`athletehubru-api`. Метки привязываются к сервисам файлом-дополнением, который живёт
только на сервере:

```bash
cd /var/www/fastuser/data/www/athletehub.ru
cat > docker-compose.override.yml <<'YAML'
# Только для боевого сервера: образы приезжают готовыми, собирать здесь нечего.
services:
  api:
    image: sporthub-api:latest
  web:
    image: sporthub-web:latest
YAML
```

⚠️ На боевом сервере **никогда** не запускать `docker compose up --build` и
`npm run app:up` (у него `--build` внутри): обе команды начнут сборку прямо здесь.
Штатный запуск на проде — `docker compose --profile app up -d`, без `--build`.

## 2. База и учётная запись

Пароль задаётся переменной `POSTGRES_PASSWORD` в `.env` рядом с `docker-compose.yml`.
Значение по умолчанию из репозитория на боевом сервере **не годится**.

```bash
cd /var/www/fastuser/data/www/athletehub.ru
printf 'POSTGRES_PASSWORD=%s\n' "$(openssl rand -base64 24)" > .env
chmod 600 .env
docker compose up -d db
docker compose logs db | tail -20
```

⚠️ Порядок здесь обязателен: **сначала `.env`, потом первый подъём базы**. Пароль и
локаль сравнения (`POSTGRES_INITDB_ARGS`) применяются ровно один раз — при создании
тома. Если база уже поднялась с паролем по умолчанию, правка `.env` её пароль не
поменяет: бэкенд будет получать отказ в доступе, а лечится это только пересозданием
тома, то есть потерей данных.

⚠️ Порт базы публикуется только на `127.0.0.1` — наружу она не смотрит. Проверить:

```bash
ss -tlnp | grep 5434     # должен быть только 127.0.0.1
```

## 3. Переменные окружения и секреты

Все значения собираются в одном файле — `.env` рядом с `docker-compose.yml`. Его читает
сам compose и подставляет в описание сервисов; приложение этот файл не видит.

⚠️ В шаге 2 файл создавался перекрытием (`>`), здесь строки **дописываются** (`>>`) —
иначе пароль базы потеряется.

```bash
cd /var/www/fastuser/data/www/athletehub.ru
cat >> .env <<'ENV'
NEXT_PUBLIC_YANDEX_MAPS_API_KEY=<ключ>
YANDEX_SUGGEST_API_KEY=<ключ>
SPORT_HUB_PUBLIC_ORIGIN=https://athletehub.ru
DATABASE_POOL_SIZE=10
ENV
chmod 600 .env
```

### Две переменные с двойной ролью

Их путали, поэтому явно.

**`SPORT_HUB_API_ORIGIN`.** Next вычисляет `rewrites()` во время сборки и записывает
готовый адрес назначения в манифест маршрутов — переменной окружения при запуске его
уже не подменить. Поэтому значение приходит **аргументом сборки** образа фронта
(`args:` в compose). Та же переменная читается **второй раз при запуске** — отрисовкой
страниц на сервере (`apps/web/src/lib/server-api.ts`), поэтому она же стоит и в
`environment:`. Пропустить любую из двух ролей — получить фронт, который ходит на
`localhost:3001` вместо соседнего контейнера. Проверить вшитое значение:

```bash
docker compose run --rm --no-deps --entrypoint sh web \
  -c "grep -o 'http://[^\"]*' .next/routes-manifest.json"
```

**`NEXT_PUBLIC_YANDEX_MAPS_API_KEY`.** Префикс `NEXT_PUBLIC_` заставляет Next подставить
значение прямо в код, который уедет в браузер, — то есть ключ вшивается на **сборке**
образа фронта. Тот же ключ отдельно нужен **бэкенду в рантайме**: прокси геокодера живёт
там (`apps/api/src/geo/geo.controller.ts`). Одно имя, два разных потребителя.

⚠️ Файлы окружения в образ не копируются намеренно (`.dockerignore`, строки 12–19):
слой образа неизменяем, вычистить из него ключ потом нельзя — только пересобрать образ
и отозвать ключ.

⚠️ **Пустой ключ выключает карту МОЛЧА, и это уже происходило.** Compose читает
переменные из `.env` в корне проекта — не из `apps/api/.env`. Пока корневого файла нет
(или в нём нет строки с ключом), `${NEXT_PUBLIC_YANDEX_MAPS_API_KEY:-}` подставляется
пустым, образ фронта собирается без ключа, и на месте карты появляется надпись
«Карта недоступна: не указан API-ключ». Ни один тест этого не ловит: страница отдаёт 200,
данные на ней есть, и выглядит всё исправным. Поймали случайной проверкой глазами.

Порядок правильный: **сначала записать ключ в `.env`, потом собирать образ фронта.**
Проверка после сборки — открыть главную и убедиться, что вместо надписи об отсутствии
ключа идёт «Загрузка карты…» и запрос к `api-maps.yandex.ru`:

```bash
curl -s http://localhost:3000/ | grep -c 'Карта недоступна'   # ожидается 0
```

## 4. Соединения с базой

`max_connections` у базы — 30 (`POSTGRES_MAX_CONNECTIONS`). Число посчитано под боевой
сервер, а не взято на глаз.

Слоты `max_connections` тратят только клиентские соединения: фоновые процессы базы
(автоочистка, запись журнала, контрольные точки) берутся из отдельного лимита и в этот
счёт не входят.

| Потребитель                      | Соединений | Когда                                            |
| -------------------------------- | ---------- | ------------------------------------------------ |
| Бэкенд, один процесс             | до 10      | постоянно (`DATABASE_POOL_SIZE`)                 |
| Разовый перенос данных           | до 10      | окно простоя: поднимает свой пул того же размера |
| Движок миграций и его блокировка | 2          | окно простоя                                     |
| Ручные `psql`                    | 3          | по необходимости                                 |
| `superuser_reserved_connections` | 3          | резерв, вычитается из общего числа               |
| **Итого в самый плотный момент** | **28**     | из 30                                            |

В установившемся режиме занято куда меньше: пул создаёт соединения лениво и закрывает
простаивающие, так что при работающем приложении в базе обычно 2–3 клиентских
соединения, а не 10.

**Вывод: 30 достаточно, менять не нужно.** На проде нет прогонов тестов — а именно они
давали локальное `sorry, too many clients already`: каждый исполнитель vitest поднимает
собственный пул того же размера, и при нескольких исполнителях плюс два приложения
потолок выбирается мгновенно.

⚠️ `DATABASE_POOL_SIZE` ставится по числу ядер VPS: пул больше числа ядер не ускоряет,
а замедляет — соединения начинают конкурировать за те же ядра. Если пул увеличивается,
`POSTGRES_MAX_CONNECTIONS` пересчитывается по той же формуле:
`пул × 2 + 2 + 3 + 3`.

## 5. Миграции и данные

Порядок обязателен: **сначала схема, потом код**. Аддитивная миграция безопасна для ещё
работающего старого кода; обратный порядок даёт окно, в котором новый код обращается
к колонкам, которых ещё нет.

⚠️ **У миграции, которая колонку УБИРАЕТ, это правило работает только под простоем.**
Старый код продолжает её читать, и сразу после наката он отвечает пятисотой на всё,
что трогает эту таблицу. Проверено на `20260910200000_drop_user_role`: контейнер
с прежним образом после дропа `users.role` уронил даже вход — клиент Prisma внутри
образа по-прежнему выбирал удалённую колонку. Поэтому для убирающей миграции приложение
на время наката обязано быть остановлено, а новый образ — подняться сразу после неё,
не «когда-нибудь потом».

**Окно простоя допустимо** (решение заказчика). На время наката приложение остановить,
чтобы никто не создал запись в тот момент, когда схема меняется под ним.

### 5.1 Проверка ПЕРЕД накатом: счётчики занятых мест

Миграция `20260821040000_schedule_booked_range` вешает на таблицу расписания ограничение
`booked_count >= 0 AND booked_count <= capacity`. Ограничение проверяется на уже лежащих
строках: если хоть одна не проходит, `ALTER TABLE` падает и вся миграция откатывается.

Счётчики протухают легко — в локальном наборе они стояли `1, 5, 4, 2, 5` при полном
отсутствии активных записей. На боевых данных набор другой, и проверить его надо своим
запросом, а не по аналогии.

```bash
docker compose exec -T db psql -U sporthub -d sporthub \
  -c "SELECT count(*) FROM schedule WHERE booked_count < 0 OR booked_count > capacity;"
```

- Ответ `ERROR: relation "schedule" does not exist` — база ещё пустая, миграции не
  накатывались ни разу. Это нормально: проверять нечего, идти дальше.
- Ответ `0` — можно накатывать.
- Ответ больше нуля — **сначала пересчитать счётчики, потом накатывать**.

Пересчёт. Занятым место считается по активной записи: статус `pending` или `confirmed`
и непустая ссылка на слот (`apps/api/src/storage/seed/prepare.ts`, тот же набор статусов
из `packages/domain/src/booking-status.ts`).

```sql
-- 1. Посмотреть, что именно разъехалось.
SELECT s.id, s.capacity, s.booked_count,
       (SELECT count(*) FROM bookings b
         WHERE b.schedule_id = s.id AND b.status IN ('pending', 'confirmed')) AS active
  FROM schedule s
 WHERE s.booked_count <> (SELECT count(*) FROM bookings b
                           WHERE b.schedule_id = s.id AND b.status IN ('pending', 'confirmed'))
 ORDER BY s.id;

-- 2. Пересчитать по фактическим активным записям.
UPDATE schedule s
   SET booked_count = (SELECT count(*) FROM bookings b
                        WHERE b.schedule_id = s.id AND b.status IN ('pending', 'confirmed'))
 WHERE s.booked_count <> (SELECT count(*) FROM bookings b
                           WHERE b.schedule_id = s.id AND b.status IN ('pending', 'confirmed'));

-- 3. Убедиться, что после пересчёта ограничение пройдёт.
SELECT count(*) FROM schedule WHERE booked_count < 0 OR booked_count > capacity;
```

⚠️ Если после пересчёта шаг 3 всё ещё показывает не ноль — активных записей на слоте
больше, чем мест. Это не арифметика, а перебронирование: разбирать вручную по каждому
слоту, отменяя лишние записи, и только потом накатывать миграцию.

⚠️ Тот же порядок действует и при каждой следующей выкатке со сменой схемы, а не только
в этот раз: на живой базе ограничения проверяются по уже лежащим строкам.

### 5.2 Накат миграций

На боевом сервере — **рабочим образом, без томов и без сборки**. Всё нужное уже внутри:
движок миграций (в Prisma 7 пакет `prisma` — рабочая зависимость `@prisma/client`),
схема и каталог миграций (`COPY` в ступень `runner`, ~120 КБ).

```bash
cd /var/www/fastuser/data/www/athletehub.ru

# Сначала посмотреть, что вообще будет накатываться — команда ничего не меняет.
docker compose run --rm api npx prisma migrate status

# Накат.
docker compose run --rm api npx prisma migrate deploy
```

Ожидаемый ответ `migrate status` на уже накатанной базе — `Database schema is up to date!`;
на пустой — список неприменённых миграций. Проверено запуском собранного образа против
живой базы.

`migrate status` печатает и число найденных миграций, и список неприменённых — сверять
надо с содержимым `apps/api/prisma/migrations/` (`ls -1 apps/api/prisma/migrations`),
а не с числом, записанным в документе: миграции добавляются, документ устаревает.

Штатный сервис `migrate` из `docker-compose.yml`
(`docker compose --profile migrate run --rm migrate`) делает то же самое, но собирает
ступень `builder` — весь монорепозиторий с зависимостями разработки. На машине
разработки это удобно, **на боевом сервере не нужно вовсе**: после того как схема
и миграции попали в рабочий образ, отдельная ступень для наката не требуется.

### 5.3 Данные

Хранилище у приложения одно — PostgreSQL, переносить данные неоткуда. Случая два.

**Чистая установка — демонстрационный набор.** Справочники (города, виды спорта, теги,
удобства) плюс минимальный работающий набор, чтобы было чем войти и было что открыть:

```bash
docker compose run --rm api \
  node -e "require('./dist/storage/seed/cli').runSeedCli('dev').then((code) => process.exit(code))"
```

⚠️ Команда `npm run db:seed` на сервере не работает: она запускает `scripts/db-seed-dev.mjs`,
а в рабочий образ попадает только собранный код. Запускающая обвязка внутри образа живёт
в `dist/storage/seed/cli.js`; запускать `node dist/storage/seed/dev-seed.js` бесполезно —
этот модуль только экспортирует функции, точки входа в нём нет.

⚠️ Сид кладёт **демонстрационные** строки. На базе с боевыми данными не запускать.

⚠️ Вся вставка идёт одной транзакцией: либо записалось целиком, либо база не тронута.
Сид идемпотентен **на своей базе**, а не на любой. Он делает `upsert` по номеру,
а почта уникальна: на базе, где номера заняты другими почтами, он падает на
`Unique constraint failed on the fields: (email)`. Восстановить чужую базу им нельзя —
только дампом (§8).

**Восстановление ранее снятой базы.** Дамп из §0 накатывается по §8. Это же единственный
способ поднять на новом сервере базу с боевыми данными.

### 5.4 Миграции фазы 35: одна убирающая и одна перестраивающая

Фаза 35 добавила **шесть** миграций. Четыре аддитивные и безобидные, две требуют внимания.

| Миграция                                     | Что делает                                                      | Чем опасна                                                                                                         |
| -------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `20260910120000_account_kind`                | добавляет `users.account_kind` и заполняет его из роли          | аддитивная; **заполнение идёт В ТОЙ ЖЕ миграции** — иначе администраторы потерялись бы между накатом и заполнением |
| `20260910180000_notes_addressee`             | лицо у заметок о клиентах                                       | аддитивная                                                                                                         |
| `20260910190000_notification_addressee`      | лицо у уведомлений плюс `CHECK` «адресат один»                  | аддитивная                                                                                                         |
| `20260910200000_drop_user_role`              | **убирает** `users.role`                                        | **только под простоем** — см. предупреждение в начале §5                                                           |
| `20260910210000_preferences_per_face`        | суррогатный ключ и три частичных индекса у настроек уведомлений | **перестраивает таблицу**: составной ключ `(user_id, type)` заменён на суррогатный                                 |
| `20260910230000_drop_quarantine_preferences` | убирает мёртвые строки настроек вырезанного механизма санкций   | аддитивная по схеме; удаляет данные, но ровно два известных типа по явному списку, а не шаблоном                   |

⚠️ **Про `preferences_per_face`.** PostgreSQL считает `NULL ≠ NULL`, поэтому обычный
уникальный индекс не выразил бы правило «один набор настроек на ящик»: у личных строк
лицо пусто, и такие строки друг другу не мешали бы. Отсюда три ЧАСТИЧНЫХ индекса —
на личные настройки, на клубные и на тренерские. Prisma частичных индексов не знает,
поэтому запись идёт «найти и обновить, иначе создать», а не `upsert`.

⚠️ **Порядок наката.** `drop_user_role` идёт после `account_kind` не случайно: вид
учётной записи обязан быть заполнен до того, как роль исчезнет, иначе восстанавливать
его будет неоткуда. Накат по порядку номеров это обеспечивает сам — не переставлять.

## 6. Проксирование, домен, сертификат

nginx не трогаем. Он проксирует на `127.0.0.1:3000`, и контейнер фронта публикует ровно этот
адрес и порт. Для nginx способ запуска приложения незаметен. Сертификат Let's Encrypt
продлевается сам.

## 7. Запуск приложения

Приложение живёт в контейнерах, других способов запуска у него нет.

```bash
docker compose --profile app up -d
docker compose --profile app ps
curl -s http://127.0.0.1:3001/api/health
```

Ожидаемый ответ проверки живости — код 200 и `"database":"up"` внутри. Код 503 означает,
что база недоступна: проверка спрашивает хранилище, а не только сам процесс.

⚠️ Если на сервере остались процессы pm2 от прежнего способа запуска — снять их
(`pm2 delete all`, затем **обязательно** `pm2 unstartup`, иначе автозапуск вернётся после
перезагрузки). Они слушают порты 3000 и 3001 — те же, что публикуют контейнеры: половина
запросов уйдёт в один процесс, половина в другой, и диагностируется это часами.

## 8. Откат

### Единственный откат — восстановление базы из дампа

⚠️ Хранилище у приложения одно — PostgreSQL, и способ запуска один — контейнеры. Отката
«на файлы» или «на pm2» не существует: этого кода нет ни в репозитории, ни в образах.
Значит дамп обязан быть снят ДО операции (§0). **Нет дампа — нет отката.**

Так решено осознанно: вторая реализация хранилища означала бы вторую реализацию под
каждую новую таблицу, и держать её ради отката, окно которого измеряется часами, дороже,
чем снять откат.

### Восстановление базы из дампа

```bash
cd /var/www/fastuser/data/www/athletehub.ru

# 1. Остановить приложение, но НЕ базу.
docker compose stop web api

# 2. Очистить схему: накат в непустую базу упрётся в уникальные ключи
#    и оставит смесь старых и новых строк.
docker compose exec -T db psql -U sporthub -d sporthub \
  -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'

# 3. Накатить дамп.
gunzip -c ~/sporthub-db-<дата>.sql.gz | docker compose exec -T db psql -U sporthub -d sporthub

# 4. Поднять приложение обратно.
docker compose --profile app up -d
curl -s http://127.0.0.1:3001/api/health
```

Ожидаемый ответ проверки живости — 200 и `"database":"up"`.

⚠️ Останавливать надо именно `stop web api`, а не `docker compose --profile app down`:
`down` относится ко всему проекту и снесёт заодно контейнер базы. Данные при этом уцелеют
(том остаётся), но база встанет — а она как раз и нужна для восстановления.

⚠️ Восстановление возвращает базу к состоянию **на момент дампа**. Всё, что клиенты
записали после — записи, отзывы, публикации, — теряется. Чем дольше приложение проработало
после снятия дампа, тем дороже откат: решение принимается в первые часы, а не через неделю.

⚠️ Дамп снят со **старой** схемой. Если после него накатывались миграции, восстановление
возвращает и схему тоже: код на сервере в этот момент надо вернуть на прежнюю метку образа
(§1.1), иначе новый код пойдёт за колонками, которых в восстановленной схеме нет.

## 9. Проверка на боевом

Полный прогон `tests/checklists/phase-33-database.md`, отдельный отчёт
в `tests/reports/`. Прогон — приёмка выкатки.

⚠️ Нагрузочный замер на боевом **не гоняется никогда**: он создаёт настоящие записи

## 10. Хранилище одно

У приложения одна реализация хранилища — PostgreSQL: на каждый токен внедрения в
`apps/api/src/storage/storage.module.ts` приходится ровно один провайдер. Ни переключателя
реализаций, ни файлов данных, ни тома `./data` у сервиса `api`, ни описания процессов pm2
в репозитории нет, и команды переноса из файлов тоже нет.

Возврат этих упоминаний в код стережёт `apps/api/src/test/storage-boundary.test.ts` —
падение этого набора означает, что в бизнес-код вернулась вторая реализация. Проверить
руками:

```bash
grep -rn 'SPORT_HUB_STORAGE\|SPORT_HUB_DATA_DIRECTORY' . \
  --exclude-dir=node_modules --exclude-dir=.git
```

Находиться должны только строки самого сторожа.

## 11. Эксплуатация

| Что                 | Как                                                               |
| ------------------- | ----------------------------------------------------------------- |
| Журналы             | `docker compose --profile app logs -f <сервис>`                   |
| Ротация журналов    | драйвер `json-file` с ограничением размера, см. ниже              |
| Расход памяти       | `docker stats`                                                    |
| Место под базу      | `docker system df -v` и размер тома `sporthub_pgdata`             |
| Состояние процессов | `docker compose --profile app ps`                                 |
| Живость приложения  | `curl -s http://127.0.0.1:3001/api/health` — 200 и `database: up` |

Ротация задаётся демону целиком, а не каждому сервису отдельно, — иначе новый сервис
приедет без ограничения и однажды забьёт диск:

```bash
cat > /etc/docker/daemon.json <<'JSON'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
JSON
systemctl restart docker
```

⚠️ Настройка применяется к контейнерам при их создании: уже работающие надо пересоздать
(`docker compose --profile app up -d --force-recreate`).

Автозапуск обеспечивает сам Docker: у всех постоянных сервисов `restart: unless-stopped`.
У разового `migrate` его нет намеренно — он отрабатывает и завершается.

## 12. Команды репозитория и где они нужны

| Команда                       | На проде | Что делает                                                         |
| ----------------------------- | -------- | ------------------------------------------------------------------ |
| `npm run app:up`              | нет      | ⚠️ содержит `--build` — начнёт сборку на сервере, см. §1.1         |
| `npm run app:down`            | нет      | на проде — `docker compose stop web api`, см. §8                   |
| `npm run app:logs`            | можно    | то же, что `docker compose --profile app logs -f`                  |
| `npm run images:build:server` | нет      | сборка образов под платформу сервера — на машине разработки        |
| `npm run db:up` / `db:down`   | можно    | подъём и остановка только базы                                     |
| `npm run db:psql`             | можно    | консоль базы внутри контейнера                                     |
| `npm run db:seed`             | **нет**  | ⚠️ демонстрационный набор; на чистой установке — команда из §5.3   |
| `npm run db:reset`            | **нет**  | ⚠️ `docker compose down -v` — сносит том базы вместе с данными     |
| `npm run db:test:clean`       | нет      | уборка схем после прогонов тестов; на проде прогонов нет, не нужна |
| `npm run test:db`             | нет      | прогон тестов; на боевом сервере не запускается                    |
