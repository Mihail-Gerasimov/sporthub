# E2E-тестирование через Playwright MCP

## Когда этот скил активируется

Триггеры от пользователя:
- "прогони чек-лист"
- "запусти E2E"
- "запусти MCP"
- "запусти Playwright"
- "проверь фазу через браузер"
- "сделай автотест"
- "протестируй вручную <функционал>"

## Инфраструктура

- **MCP-сервер:** `@playwright/mcp@0.0.53` (пин версии, не `@latest` — в свежих версиях баги с console и output-dir).
- **Конфиг:** `.mcp.json` в корне проекта.
- **Приложение:** фронт `http://localhost:3000`, бэкенд `http://localhost:3001` — оба процесса должны быть подняты ПЕРЕД запуском чек-листа, вместе с базой. Локально: `npm run db:up`, `npm run db:seed`, затем `npm run start --workspace @sporthub/api` и `npm run dev --workspace @sporthub/web`. Всё в контейнерах — `npm run app:up`.
- **Чек-листы:** `tests/checklists/phase-XX-*.md` или `tests/checklists/feature-*.md`.
- **Скриншоты падений:** `tests/screenshots/phase-XX/` (подпапка создаётся автоматически).
- **Отчёты прогонов:** `tests/reports/phase-XX-<ISO-timestamp>.md`.

## Preflight-проверки перед прогоном

1. Проверить что приложение доступно: `browser_navigate` на `http://localhost:3000` — если таймаут или ECONNREFUSED, СТОП и сказать пользователю поднять фронт и бэкенд. Пустой каталог на главной означает незасеянную базу — тогда `npm run db:seed`.
2. Проверить что MCP-сервер подключён: если `browser_*` тулы недоступны, СТОП и сказать пользователю перезапустить Claude Code.
3. Прочитать чек-лист полностью ДО старта прогона — не исполнять на ходу.

## Auth — только через API, не через UI-форму

- **Запрещено** проходить UI login-форму в чек-листах. Долго, ненадёжно, не тестирует то что нужно.
- Первый шаг любого чек-листа — `browser_evaluate` с fetch на auth API:

```js
await fetch('/api/auth/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email: '<email>', password: '<password>' })
}).then(r => r.json())
```

⚠️ **Поля `accountType` в теле входа НЕТ** — его убрал шаг 35.22 вместе с ролями,
и схема стала строгой: лишнее поле отвергается с 400. Кем человек является
на площадке, решает не форма входа, а то, какими лицами услуг он владеет.

**Администратор входит СЛУЖЕБНЫМ входом** — тем же маршрутом, но с признаком
`portal: 'service'`:

```js
body: JSON.stringify({ email: 'admin@sporthub.local', password: '<password>', portal: 'service' })
```

Признак проверяется в обе стороны: администратор без него получает 403
«Администраторы входят через /service-portal», обычный человек с ним — тоже отказ.
Через интерфейс тот же вход живёт на странице `/service-portal`.

- Личность живёт в серверной сессии: сервер ставит cookie `HttpOnly`, браузеру она недоступна и в `localStorage` ничего не пишется.
- Поэтому после логина **обязателен** `browser_navigate` (или перезагрузка) — стор наполняется только ответом `GET /api/auth/me` при монтировании страницы (`SessionBootstrap`). Кликать по странице, открытой до логина, бессмысленно: она всё ещё гостевая.
- Учётки берутся из сида `apps/api/src/storage/seed/dev-seed.ts` — по одной на каждый
  НАБОР ЛИЦ, а не на роль: без лиц, с карточкой тренера, с клубом, с обоими, плюс
  администратор. Общий пароль объявлен там же константой `DEV_PASSWORD`.
- ⚠️ **На живой базе состав другой.** Проверять его запросом, а не по памяти:
  `SELECT u.email, (SELECT count(*) FROM clubs c WHERE c.managed_by_user_id=u.id) AS clubs,
  (SELECT count(*) FROM trainers t WHERE t.managed_by_user_id=u.id) AS cards FROM users u;`
- Чек-лист называет не роль, а НАБОР ЛИЦ («человек без лиц», «владелец клуба
  и карточки»). Брать учётку с подходящим набором.

## Правила выполнения шагов

1. **После `browser_navigate`** всегда ждать post-hydration элемент через `browser_wait_for({ text: "..." })` ПЕРЕД любым кликом. Не кликать на свежую страницу сразу — React 19 может не успеть повесить обработчики.
2. **`browser_snapshot`** вызывать только когда нужны свежие `ref`-идентификаторы — не после каждого шага. Экономия токенов.
3. **`browser_take_screenshot` — ТОЛЬКО на падениях.** Формат имени: `phase-XX/step-{id}-FAIL-{YYYY-MM-DDTHH-mm-ss}.png`. Сохранять в подпапку фазы — подпапка создастся автоматически.
4. **На падении НЕ прерывать прогон.** Помечать шаг `failed`, зависимые шаги `blocked`, идти к следующему независимому шагу.
5. **На каждом падении собирать:**
   - expected vs actual (что ждали, что получили)
   - URL на момент падения
   - последние error-уровня console через `browser_console_messages({ level: "error" })`
   - путь к скриншоту
6. **Тяжёлые страницы** (логи, analytics, dashboard с большими таблицами) — не снапшотить body целиком. Использовать scoped snapshot по конкретному контейнеру или проверять через текстовые ассерты.
7. **В конце прогона** писать отчёт через Write-tool в `tests/reports/phase-XX-<ISO-timestamp>.md`.
8. **Закрыть браузер** через `browser_close` в самом конце.

## Формат чек-листа (как пользователь должен писать)

```markdown
# E2E: Phase XX — <название>

**Role:** admin
**Base URL:** http://localhost:3000
**Preconditions:** база засеяна (`npm run db:seed`), фронт и бэкенд подняты

## Scenario: <название сценария>

- [ ] **step-1** Login как admin через `POST /api/auth/login` с `portal: 'service'`
- [ ] **step-2** Navigate /service-portal/logs — expect heading "Логи системы"
- [ ] **step-3** Assert таблица логов с >= 1 строкой
- [ ] **step-4** Click кнопку "Фильтр по дате" — expect popup открылся
- [ ] **step-5** Fill поле "С" значением "2026-04-01"
- [ ] **step-6** Click "Применить" — expect таблица обновилась за < 5s
```

**Якорь `**step-N**` обязателен** — по нему отчёт ссылается на шаги.

## Запреты

- **НЕ** использовать `playwright test` / `.spec.ts` — у нас другой workflow через MCP.
- **НЕ** мокать API через `page.route()` — тестируем реальные endpoints работающего приложения.
- **НЕ** логиниться через UI-форму — только через `/api/auth/login` (администратор —
  с признаком `portal: 'service'`; поля `accountType` в теле больше нет вовсе).
- **НЕ** включать `--headless` в `.mcp.json` — окно браузера должно быть видимо для визуального контроля пользователем.
- **НЕ** снапшотить body целиком на тяжёлых страницах — использовать scoped snapshot или текстовые ассерты.
- **НЕ** прерывать прогон на первом падении — пройти весь чек-лист, собрать все фейлы сразу.

## После прогона

- Путь к отчёту вывести пользователю в чат.
- Количество passed/failed/blocked шагов кратко.
- Если были падения — перечислить их ID.
- Ждать указаний пользователя: "фиксим step-2", "прогони повторно" и т.д.
