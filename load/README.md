# Нагрузочный замер

Замер отвечает не на вопрос «выдержит ли», а на вопрос **что упрётся первым и на каких числах**.
Результат — таблица времени отклика, доли ошибок и расхода памяти, записанная в отчёт фазы
с датой и условиями машины. Требования к серверу выдаются по замеру, а не наугад.

## Как гонять

```bash
# База и бэкенд подняты, данные на месте
npm run db:up
npm run start --workspace @sporthub/api

# Три профиля одновременно, 40 виртуальных пользователей, 2 минуты
k6 run load/k6-scenarios.js

# Другие рамки
k6 run -e VUS=100 -e DURATION=3m -e API=http://127.0.0.1:3001 load/k6-scenarios.js

# Только гонка за последним местом: нужен слот ровно с одним свободным местом
k6 run -e ONLY=race -e RACE_SCHEDULE_ID=<номер слота> load/k6-scenarios.js
```

Расход памяти снимается отдельно и одновременно с прогоном:

```bash
docker stats --no-stream --format '{{.Name}} {{.MemUsage}}'
```

## Правила

- ⚠️ **На боевом сервере не гоняем никогда.** Замер создаёт настоящие записи и меняет статусы.
- Профили работают **одновременно**, а не по очереди. Прогнанный в одиночку профиль меряет не то:
  вся суть в том, что атлеты, провайдер и админ работают в одну и ту же минуту.
- Отдельная метрика на профиль. Общий показатель усреднил бы дешёвое чтение справочника
  с дорогой сводкой админа и скрыл бы, что именно тормозит.
- Профиль гонки проверяет **корректность, а не скорость**: десять одновременных запросов
  на слот с одним местом обязаны дать ровно один успех. Два — это овербукинг.
- Данные замера помечаются и удаляются после прогона одной командой.

## Пороги

| Метрика | Порог | Что означает превышение |
| --- | --- | --- |
| `error_rate` | < 1% | запросы падают под нагрузкой |
| `profile_athlete` p95 | < 1.5 с | каталог тормозит у большинства посетителей |
| `profile_provider` p95 | < 2 с | кабинет провайдера тормозит |
| `profile_admin` p95 | < 3 с | сводка и журнал упираются в полный перебор |
| `race_won` | ровно 1 | больше одного — овербукинг, ноль — слот был занят до замера |
| `race_unexpected` | 0 | отказ по причине, не связанной с нехваткой мест |

## Профиль `mailbox` — ящик лица (фаза 35)

```bash
k6 run -e ONLY=mailbox load/k6-scenarios.js
```

Меряет два запроса, которые фаза 35 сделала горячими:

- **ответ «кто я»** — он теперь возит лица человека (клубы и карточки тренера);
- **лента по лицу** — она спрашивается отдельно для каждого лица плюс личная.

Отдельным профилем, а не внутри кабинетных, потому что эти два запроса ходят
на **каждой** странице кабинета, а не раз за сессию: если они дороги, дорого
становится всё. Порог у профиля жёстче кабинетных — `p(95) < 800 мс`.

Учётная запись по умолчанию — `both@sporthub.local`: у неё два лица, клуб
и карточка тренера. На человеке без лиц профиль померяет только личный ящик
и ничего не скажет про то, ради чего заведён.

Переопределяется: `-e MAILBOX_EMAIL=...`.
